# Spike 2143 — is wasm SQLite faster than the engine we ship today, on our workload?

Measured 2026-09-18. Ticket: [wcpos/monorepo#2143](https://github.com/wcpos/monorepo/issues/2143).
Three engines behind rxdb-premium's worker RPC — the shipped OPFS filesystem worker
(`apps/main/public/opfs.worker.js`, verbatim), premium SQLite on the official SQLite wasm build with
the `opfs-sahpool` VFS (WAL, one translated statement per query, `ANALYZE` after the seed), and
premium IndexedDB (relaxed durability, as it ships) — on the same throwaway schemas with the
missing indexes declared, replaying the POS's real query and write shapes at 2,000 and 20,000
products/orders. Page-visible time through the RPC is the only timing. Every sample's content is
SHA-256-checked across engines; every run reported here passed. The harness decides nothing; the
tables are below the answers, generated by `report.mjs` from `results.*.json`.

**Environments.** Mac: Apple M4 Pro, macOS 25.6.0 — Chrome 154.0.8037.44, Firefox 153.0, Playwright
WebKit 26.5. Windows: GitHub `windows-latest` (Windows 10.0.26100, AMD EPYC 7763 shared runner),
Chrome 152.0.7977.83 — a CI VM, so its absolute numbers are slower than any till; read its ratios.
rxdb / rxdb-premium 17.4.0, `@sqlite.org/sqlite-wasm` 3.53.4-build1, esbuild 0.28.2, Node 24 (Mac) / 22 (Windows).

## Answers

**1. Who wins what.** The workload splits cleanly into three families, and the same engine wins each
family in every browser measured (large scale, p50; Chrome / Firefox / Windows-Chrome):

- **Indexed and pushed queries: SQLite, by two to three orders of magnitude.** The Orders default
  scope find (`$elemMatch` ×2, sorted, limit 10) goes from 131 / 303 / 397 ms on the shipped engine
  to 1.2 / 6.2 / 2.5 ms; a 100-id `remoteId $in` (every reconciliation query) from 95 / 205 / 330 ms
  to 1.2 / 2.5 / 2.5 ms and its count from 94 / 199 / 318 ms to 0.2 / 0.9 / 0.7 ms; the *hypothetical*
  pushed products grid (sort by name, limit 10) from 656 / 307 / 2,667 ms to 0.3 / 0.9 / 0.6 ms —
  the shipped engine's own sorted-limit path is slower than its unsorted full read. IndexedDB sits
  between the two, 3–15 ms on the pushed grid but 220–750 ms on the `$in` and the orders scope.
- **Whole-table reads: the shipped engine, by 3–8× on a Mac and 10–40× on the Windows runner.**
  The catalogue-blob read (every product document, what `catalogue-search-blob.ts` does on every
  open to build the search index) is 89 / 177 / 281 ms shipped versus 2,410 / 1,440 / 10,713 ms on
  SQLite and 285 / 610 / 1,059 ms on IndexedDB. The products grid *as issued today* (no pushed sort,
  15,337 rows to JS) is 176 / 256 / 489 ms shipped versus 579 / 656 / 2,276 ms SQLite. The two
  unindexable orders paths behave the same way: the `$elemMatch` count is 130 / 309 / 399 ms shipped
  and 1,673 / 1,615 / 7,160 ms on SQLite (a JSON scan of 20k orders), the open-status read (12,000
  rows) 222 / 349 / 662 ms versus 1,696 / 1,139 / 7,550 ms. The shipped engine is fast here because
  it is a memory-resident store — the same property that makes it undurable (research §1); SQLite
  pays wasm-to-JS marshalling per byte returned, and the Windows runner pays it hardest.
- **Small writes: IndexedDB, then SQLite, then the shipped engine — and the shipped engine's write
  cost grows with the table.** The three-write cart line add (whole-document update, queue insert,
  dirty-mark update) is 20 / 36 / 61 ms shipped at 20k orders (3 / 8 / 8 ms at 2k), 6.0 / 3.1 / 31 ms
  on SQLite, 0.6 / 0.9 / 3.0 ms on IndexedDB. Order create: all three under 4 ms on a Mac, 16 ms
  worst case (SQLite) on the runner. Cold open to first read on a 20k database: SQLite 72 / 82 ms on
  the Mac but **2,540 ms on the Windows runner** — unchanged by the ANALYZE fix, so not the planner;
  suspected sync-access-handle acquisition for the 64-handle pool, to be measured on a till and
  sized to the collection count — shipped 130 / 274 / 326 ms (it loads the store into memory),
  IndexedDB 8 / 13 / 22 ms; SQLite's payload is
  723 KB of worker plus 869 KB of wasm against 124 KB for the shipped worker. A full resync of 20,000
  products costs 3.6 / 4.4 / 18.3 s on SQLite against 1.0 / 1.9 / 3.1 s shipped. Disk: SQLite
  201 MB for the large seed against 151 MB shipped and 152–273 MB IndexedDB (`navigator.storage.estimate`).

**2. The bracket.** Chrome-on-Mac and Firefox-on-Mac agree on the winner of every cell family
above, and so does Windows Chrome: at the large scale the bracket table below shows no straddle on
any cell across the three columns that measured all engines (the WebKit column ran IndexedDB only
and is excluded from the flag); the three small-scale straddles are sub-millisecond ties and the
2k-row full read, where a memory-resident store and a scan cost the same. Windows does not
overturn the Mac reading; it widens it: SQLite's scan-shaped costs are 4–5× Mac Chrome's on the
runner while its indexed costs stay in low milliseconds, so the penalty for the whole-table family
is larger on the platform that carries most tills. The WebKit leg is missing: Playwright's WebKit
26.5 fails the first 1,000-document OPFS write with `UnknownError: The operation failed for an
unknown transient reason` on **both** OPFS engines (shipped and sahpool), so only its IndexedDB row
ran (results.webkit.json); a Safari reading needs a human-driven Safari, not Playwright.

**3. What this decides and what it does not.** Wasm SQLite is not simply "faster on our workload":
it is faster on every query the app *could* push and slower on every read the app makes *today*
that returns whole documents — and today's two most frequent storage operations, the products grid
(no pushed sort) and the search-index build (a full read on every open), are both of the second kind.
So the speed criterion is conditional on three pieces of engine-migration work already on the map:
(i) push the products sort and limit to storage (the hypothetical `pushed` cells; a query-layer
change, not an engine one); (ii) stop building the search index from whole documents — a
projection of name/sku/barcode, or FTS5 ([#2147](https://github.com/wcpos/monorepo/issues/2147),
which this makes the tiebreaker it was suspected to be); (iii) promote `_pos_user`/`_pos_store` to
indexed columns so the orders scope and its count stop scanning JSON (spike 2145's finding,
[#2150](https://github.com/wcpos/monorepo/issues/2150)). With those, SQLite wins the interactive
paths by orders of magnitude and the cart write by 3–7×; without them it regresses grid open and
search-index build by 3–40× depending on platform. Not decided here: durability (the crash harness,
[#2144](https://github.com/wcpos/monorepo/issues/2144)), the leader-tab topology on which the
sahpool numbers depend ([#2146](https://github.com/wcpos/monorepo/issues/2146)), and anything about
native. IndexedDB's numbers are with relaxed durability and are an anchor, not a candidate.

## Two defects the harness found on the way

- **Premium SQLite's `findDocumentsById` is a full scan until `ANALYZE` runs.** Its statement adds
  `AND deleted = 0`; with no statistics SQLite's planner serves that from the deleted-leading RxDB
  expression index and walks every live row: 10 ids at 20k products cost **2,145 ms in Chrome,
  410 ms in Firefox, 9,345 ms on the Windows runner** (first runs, superseded; post-fix 0.2 / 0.4 / 0.6 ms), 0.9 ms at 2k. The same
  statement without the clause is 0.12 ms; after `ANALYZE` (840 ms once) the plan is `SEARCH ...
  USING PRIMARY KEY` and the fetch is 0.2 ms. Evidence: `probe.mjs` → `probe-findbyids.chrome.json`.
  Premium only runs `pragma optimize` in `cleanup()`. The SQLite row therefore runs `ANALYZE` after
  the seed, as an engine migration would after a resync; this is the search-hit fetch on every
  keystroke, so the migration must own it (statistics after resync, or a patched statement).
- **Playwright WebKit cannot write 1,000 × 2 KB documents through OPFS** (above). Not a Safari finding.

## Method and limits

- Page-visible elapsed times include premium's worker RPC; no worker-side timing is reported. One
  discarded warm-up precedes each cell; N = 7, N = 25 for the two write cells, N = 3 for full seeds
  and cold reads. p50/p95 by nearest rank (with N ≤ 7, p95 is the max). Raw samples are in the JSON.
- Engines run in a fixed order in fresh browser contexts and database names; small before large.
  The SQLite row wraps `query`/`count` to run one translated statement for the selectors this
  workload uses (the in-harness equivalent of 2145's proposed premium patch); unsupported selectors
  fall through to premium; the primary key maps to the `id` column. `ANALYZE` runs once after the
  seed on that row only. Premium IndexedDB is as shipped (relaxed durability); there is no raw
  IndexedDB anchor.
- `products-grid-asShipped` returns the complete matching set, which is what the app's query layer
  asks for today. `products-grid-pushed-*` are hypothetical. No-sort finds carry RxDB's normalized
  primary-key sort. Counts use RxDB's count normalization.
- Fixtures are deterministic (seeded PRNG): products ~2,000 JSON bytes shaped like
  `searchFixturePayload()`, orders ~2,700 bytes with 1–8 line items and 6–10 meta entries. Cross-engine
  checks compare canonical, revision-independent content per sample; a mismatch aborts the run.
- Cold reads reload the page in the same context (not an OS cache purge) and include worker
  creation, storage open and the first `findDocumentsById`. Routing serves bundles from memory, so
  no download latency is modelled; bundle bytes are uncompressed disk sizes.
- `storage-estimate` is origin-wide, browser-reported usage right after the large seed.
- Windows ran on a shared GitHub runner from a bundle built on Ubuntu (`spike-2143-benchmark.yml`);
  the bracket table treats it as a fourth browser column.
