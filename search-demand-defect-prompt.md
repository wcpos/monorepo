Diagnose and fix a native-only search defect in wcpos/monorepo (branch off `main`, worktree): **on native, searching for a product that hasn't synced yet returns nothing — the search-demand lane never materializes the server match — until the initial catalog backfill happens to deliver the record, which can take 40+ minutes on slow devices.** Cashier impact: after first login on a large store, search cannot find most of the catalog for the length of the initial sync. On web the same search materializes server matches in seconds (the whole `search-probe` create-and-find E2E pattern depends on it and passes).

Full evidence trail: wcpos/monorepo#1614, comment of 2026-08-28 ("New app defect: native search does not demand-fetch during initial backfill"). Summary of what is already proven — do not re-derive it:

1. **Server side is fine.** `GET https://dev-pro.wcpos.com/wp-json/wc/store/products?search=WCPOS+E2E+Variable` returns the suite fixture (id 107940, published, catalog-visible). The record is also POS-visible: an Android phone CI job synced and rendered `variable-product-tile-107940` once backfill completed.
2. **Native repro (three independent observations, CI tablet twice + local emulator).** Fresh login as `demo`/`demo` on `https://dev-pro.wcpos.com` (store "AL 12345 Store" #24128), then type `WCPOS E2E Variable` into the POS product search: zero results for 10+ minutes, retyping included, while searches for already-backfilled records ("Beanie", "Hoodie") return instantly. Footer census stayed "Mostrando 0 de 204".
3. **Backfill stalled at 104/204** on the health screen for ~10 minutes while the app sat on the search/health screens — secondary question below.
4. **The demand requirement is emitted in shared code**: `packages/core/src/query/query-state-translator.ts` (~line 420) pushes `{ kind: 'search', collection, term }` for products/customers/variations, and `packages/sync-engine/src/require-plane.ts` defines the search plane. So the wiring exists on both platforms; the question is where it dies on native — never fired, fired-but-request-never-sent (starved/queued behind backfill lanes), sent-but-response-not-materialized, or materialized-but-not-matched-by-the-local-search-index.
