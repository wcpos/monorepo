# How `@wcpos/components` evolves without losing the ledger

_Produced 2026-09-18 for [wcpos/roadmap#338](https://github.com/wcpos/roadmap/issues/338) (part of [#282](https://github.com/wcpos/roadmap/issues/282)). Branch: `research/library-evolution`, cut from `origin/next` at `aebda38456`._

**Read for this:** `packages/components/package.json`, `packages/components/src/**` (58 component folders, `lib/`, jest config), `apps/main/global.css`, `apps/main/metro.config.js`, `packages/core/jest.config.js`, root `tsconfig.json`; the [behaviour ledger](https://github.com/wcpos/monorepo/blob/research/component-ledger/.claude/research/2026-09-12-component-behaviour-ledger.md) (262 lines, 58 components) and the [cohesion audit](https://github.com/wcpos/monorepo/blob/research/design-cohesion/.claude/research/2026-09-12-design-cohesion-audit.md); primary docs for shadcn/ui, react-native-reusables, Uniwind, Primer React, Polaris and MUI (URLs cited in place). No installs, builds or tests were run.

## At a glance

- The blast radius is not evenly spread: **five specifiers carry 1,030 of the 1,988 imports** (`text` 342, `button` 207, `vstack` 195, `hstack` 192, `icon` 94), and the deep ledgers sit on components almost nobody imports directly (`virtualized-list` 19 lines / 8 imports, `tree-combobox` 14 / 5, `dnd` 12 / 3). Restyling is cheap where the ledger is thin and the ledger is deep where restyling is not the point.
- **Every resolver in this repo already maps `@wcpos/components/*` to `packages/components/src/*` by wildcard** — root `tsconfig.json`, `apps/main/metro.config.js:46`, `packages/core/jest.config.js:69` — and `apps/main/global.css:7` scans `packages/components/src/**`. A new subpath tier inside the package therefore costs **zero build-config edits**; a sibling package costs a new entry in each of those four places plus a workspace package, tsconfig, eslint config and dependency edit.
- **Recommendation: (d) token-first, with (c) as the escape hatch for the handful of components whose behaviour actually changes.** The cohesion audit already found the redesign is mostly a change of shared defaults; option (d) moves no ledger lines at all, and `src/v2/<name>` under the existing package is available per-component without paying for it up front.

## The library today

**Shape.** `packages/components/package.json` exports 64 explicit subpaths — one per component `index`, plus `combobox/types`, `data-table/types`, `format/address` and four `lib/*` helpers. There is no barrel: every call site imports a leaf. 58 component folders (`lib/` and three `*.d.ts` files are not components — the ledger's count, not the ticket's 59). 193 source files / ~20k lines excluding the 137 generated icon components.

**Dependencies.** `@rn-primitives/*` at `^1.5.2` — 22 packages, imported from **29 of the 58 folders**; `slot` (22 imports), `types` (13), `select` (12) and `hooks` (10) dominate, so most of the primitives surface is composition glue, not widget behaviour. Peer deps are the native runtime (`@shopify/flash-list`, `expo-image`, `expo-haptics`, `react-native-webview`, `react-native-gesture-handler`, `react-native-worklets`). `uniwind` is a direct dependency pinned at `1.11.0` in `package.json`, but `pnpm-lock.yaml` resolves **`uniwind@1.10.1`** — the gap #284 already flagged, and it still stands on `next`.

**How variants are done.** `class-variance-authority` `cva`, called at module scope, one or two catalogues per component. `packages/components/src/button/index.tsx` is the template: `buttonVariants` (40 variants × 7 sizes) and `buttonTextVariants` in the same file, merged through `cn` (`clsx` + `tailwind-merge`, `src/lib/utils.ts`). Colour and size reach the label through **`TextClassContext`** (`src/text/index.tsx:11`), a React context the Button fills with `buttonTextVariants(...)`; `src/text/index.tsx` composes `cn(textVariants({variant}), textClass, className)`, so the context wins over the base and the call site wins over both. The cohesion audit names this mechanism as one of the five things not to touch.

**Shared internals under `lib/`** — beyond `cn`: `portal-container.ts`, `set-ref-value.ts`, `use-hierarchy.ts`, `use-arrow-key-navigation.ts`, `multi-select.ts`, `native-popover-sizing.ts`, `phone-sheet.tsx`, `use-is-phone.ts`, `use-layout-width.ts`, `get-color-variable.ts` and `overlay-motion.ts` (the four shared duration constants introduced by the September overlay batches). Cross-folder relative imports are dense: `../lib` 77, `../text` 42, `../icon` 16, `../button` 8, `../icon-button` 8, `../hstack` 7. **Any component that moves folder rewrites those relative imports in both directions** — a new folder tier means `../lib/utils` becomes `../../lib/utils`.

**The nine file-level platform splits** — `collapsible/primitives.web.tsx`, `dnd/index.web.ts`, `image/index.web.tsx`, `keyboard-controller/index.web.tsx`, `tooltip/index.web.tsx`, `webview/index.web.tsx`, `select/trigger.web.tsx`, `toast/sonner.web.tsx`, `virtualized-list/virtualized-list.web.tsx`. A further fifteen branch inline on `Platform.OS`. These are Metro resolution, not import-path resolution: the specifier never names the platform, so a restyle that does not rename the file inherits the split for free.

**Tokens.** `apps/main/global.css` (663 lines) is the only token sheet: `@import 'tailwindcss'` + `@import 'uniwind'` + `tw-animate-css`; three `@source` lines (`apps/main/app`, `packages/components/src`, `packages/core/src`); `@theme static` and `@theme` for the scale (`--text-3xs`…`--text-sm`, `--width-*`, `--border-width-hairline`, `--duration-750`) and the semantic colour aliases (`--color-primary: var(--primary)` and ~35 siblings); then `@layer theme { :root { @variant light {…} @variant dark {…} … } }` with the oklch values per theme; then `@layer base` (web `font-size: 87.5%`, `@media ios/android` back to 100%). The control core the audit named lives in four files, not the CSS: `h-10 … rounded-md` in `input/index.tsx:39`, `button/index.tsx:117` (`size.default`), `select/index.tsx:126,143,303` and `combobox/combobox.tsx:136`.

**Tests.** 42 test files across 21 folders, jest with `ts-jest` + `jsdom` and `moduleNameMapper: {'^react-native$': 'react-native-web'}` (`packages/components/jest.config.js`). Coverage is uneven and follows the ledger, not the usage: `virtualized-list` has five, `select` four, `form` four, `lib/` five; `button` has two (`button-disabled-state`, `button-pill`); `vstack`, `hstack`, `icon`, `dialog`, `modal`, `card` have none. **jsdom jest has no platform-extension resolution** (stated in `packages/core/jest.config.js:71`), so a `.web.tsx` file is only tested when a test imports it by its literal path — which four do (`select/trigger.web.test.tsx`, `toast/sonner.web.test.ts`, `virtualized-list/virtualized-list.web.test.tsx`, `webview/index.web.test.tsx`).

**Top ten (expensive to change):** `text` 342, `button` 207, `vstack` 195, `hstack` 192, `icon` 94, `suspense` 81, `error-boundary` 79, `select` 56, `toast` 54, then `form` and `dialog` tied at 51. Six of those ten carry a *thin* ledger (`vstack` 0, `hstack` 0, `icon` 3, `suspense` 2, `error-boundary` 2, `text` 2) — they are expensive to touch and cheap to preserve. `select` (17), `form` (12), `dialog` (10), `toast` (6) and `button` (13) are the ones that are expensive on both axes.

**Used from fewer than three files (cheap to change):** `accordion`, `format/address`, `hover-card`, `lib/set-ref-value`, `numpad`, `pressable`, `print/row` (1 file each); `data-table/types`, `keyboard-controller`, `lib/portal-container`, `list-item`, `logo`, `sort-icon`, `textarea` (2 each). **Never imported from core or main at all:** the `data-table` component (only its `types` subpath is used), `toggle` (reached only through `variations-popover`'s own use of the family and through `form`), `tree-select` (its `INDENT_PX` is imported by `tree-combobox` only). Those three are dead weight a rebuild can drop with a one-line note.

**Relative imports that break on a move.** Inside `packages/components/src`, 205 cross-folder relative imports resolve one level up (`../lib` 77, `../text` 42, `../icon` 16, `../types` 8, `../icon-button` 8, `../button` 8, `../hstack` 7, `../combobox` 6, `../vstack` 4, `../input` 4, and sixteen more folders at 1–3 each). Moving a component into `src/v2/<name>` rewrites every one of its outbound `../x` to `../../x` and every inbound reference from a sibling that still points at the old folder. This is the one real cost of any option that changes folder depth, and it is mechanical, not risky.

## Option (a) — restyle in place

**Mechanics.** Edit the `cva` catalogues and class strings in the 58 existing folders. No `package.json`, resolver, `@source` or call-site change anywhere. The files touched are exactly the files the ledger documents.

**The ledger.** All 262 lines **stay**, in the files that cite them, at the line numbers the ledger quotes (which drift but stay in the same file). This is the only option with no copy, no move and therefore no silent loss: a dropped line is a deletion in a diff a reviewer can see. The risk is the inverse — a line is *preserved as text* while the restyle changes the behaviour it guards (e.g. `button/index.tsx`'s `const disabled = !!(props.disabled || loading)` comment survives a rewrite of the Pressable that drops the explicit `disabled` prop).

**Coexistence on `next`.** There is none to manage — and that is both the appeal and the problem. The moment a component lands restyled, every one of its call sites wears the new skin: `text` and `button` alone repaint 549 call sites in one commit. Half-migrated means *half the components restyled across all screens*, not half the screens migrated. A screen cannot mix old and new. The register work landing on `next` (roadmap #268–#274) inherits the new skin mid-flight whether or not those PRs have been visually reviewed, and `packages/components` is already hot — **106 commits since 2026-08-01**, including the four September overlay batches (#1974, #1985, #1989, #1991) and the tender-pane slice — so restyle commits and behaviour commits will conflict in the same files continuously.

**Release cut mid-migration.** The worst of the four. 1.11.0 ships from `next`, and a cut lands whatever mix of restyled and un-restyled components exists that day, with no flag to fall back to. Every partially-restyled control is visible to merchants.

**Platform splits.** Free. The `.web.tsx` files are edited alongside their native siblings; the specifier never changes.

**Testing.** The 42 existing tests stay put and keep running; none move or duplicate. Class-string assertions break where they exist (`tabs/tabs-list.test.tsx`, `select/trigger.test.tsx`, `badge/badge.test.tsx` assert on rendered classes) — a handful, not a rewrite.

**Review gate.** Cheapest to enforce and hardest to trust: the gate is a per-component checklist against the ledger section, checked against a diff that contains no copy of the old code. Nothing structural stops a reviewer from waving through a line that silently stopped being true.

## Option (b) — a sibling package

**Mechanics.** A new workspace package (name to be chosen; `@wcpos/ui` is taken by the plugin repo's WP-admin library per wiki ADR 2026-04-15). Costs, concretely: `packages/<new>/package.json` with its own exports map and a copy of the `@rn-primitives` + peer-dep block; `packages/<new>/tsconfig.json`, `eslint.config.mjs`, `jest.config.js`; a `paths` entry in root `tsconfig.json`; an entry in `workspaceSourceRoots` in `apps/main/metro.config.js:44-53`; a `moduleNameMapper` line in `packages/core/jest.config.js` (and `apps/main/jest.config.js`); a fourth `@source` line in `apps/main/global.css`; and a dependency edit in `apps/main/package.json` — **which is a native-fingerprint input, so it can force a metered EAS build** (memory: `apps-main-package-json-is-a-native-fingerprint-input`).

**The ledger.** Lines **copy**. This is the option that loses them: a copied file starts a new git history, so `git log --follow` on the new package returns the copy commit and nothing before it — exactly the failure mode the ledger already documents for the `2185fd1be3` vendoring commit, where `collapsible`'s history "understates" it. Every line that is only evidenced by a commit (not by a verbatim comment) is invisible in the new package unless it is re-transcribed. The ledger becomes the *only* record, and the record is on a research branch, not in the code.

**Coexistence.** Best of the four on paper: a screen imports from one package or the other, migration is per-screen, and register PRs keep landing on the old package untouched. In practice two `Portal` hosts, two `TextClassContext`s and two toast singletons coexist — `lib/portal-container.ts`, `@rn-primitives/portal` and the `sonner` host are process-global, so a new-package Dialog opened from an old-package screen has a real chance of portalling into the wrong host. Mixing within one screen is possible for layout but not for the overlay family.

**Release cut.** Safest: the old package is untouched, so a cut mid-migration ships whatever screens have moved and everything else exactly as before. This is the strongest argument for (b).

**Platform splits.** Copy as files; free but duplicated. Nine `.web` files now exist twice, and a fix to a split (the kind the ledger is full of — `8278ba5598` patched seven files at once) must be applied twice for as long as both packages live.

**Testing.** 42 test files duplicate. Both copies run in CI; the old ones keep passing against code nobody ships, which is worse than deleting them because it reads as coverage. Fixes land in one copy.

**Review gate.** Most expensive: for each component the reviewer needs the old file, the new file and the ledger section side by side, and must decide per line whether it survived a rewrite that shares no text with the original.

## Option (c) — a versioned subpath in the same package

**Mechanics.** `packages/components/src/v2/<name>/index.tsx`, exported as `@wcpos/components/v2/<name>`. **The resolvers already handle it**: root `tsconfig.json` maps `@wcpos/components/*` → `packages/components/src/*`, `apps/main/metro.config.js:46` joins the subpath onto `packages/components/src`, `packages/core/jest.config.js:69` maps `^@wcpos/components/(.*)$` → `../components/src/$1`, and `apps/main/global.css:7` already scans `packages/components/src/**/*.{ts,tsx}`. The only edit is `packages/components/package.json`'s `exports` — one entry per v2 component, or a single `"./v2/*": "./src/v2/*/index.tsx"` wildcard. Zero new dependencies, zero new config files, no `apps/main/package.json` change and therefore **no fingerprint risk**. `lib/`, `@rn-primitives` and the peer deps are shared by construction.

**The ledger.** Lines **move with the file** if the v2 component is created with `git mv` + rewrite (history follows; `--follow` keeps working), or **copy** if it is authored fresh beside the old one. The honest reading: for a component whose behaviour genuinely changes, this is a copy with the same evidence problem as (b) — but scoped to the handful of components that need it rather than all 58, and with the old file sitting in the same package one directory away, so a reviewer can diff them without leaving the repo.

**Coexistence.** Per-component and per-call-site, which is finer than (b): a screen can import `@wcpos/components/v2/button` and `@wcpos/components/select` in the same file, and the register PRs keep importing today's specifiers with no edit. The overlay caveat from (b) applies in a *weaker* form: v2 components share `lib/portal-container` and the same `@rn-primitives/portal` singleton, so there is one portal host, not two. Tailwind class generation does not care — one `@source` glob covers both tiers and one stylesheet serves both.

**Release cut.** As safe as (b): un-migrated screens import the un-migrated specifier, so a cut ships a mixture that was always intentional per call site.

**Platform splits.** Carry as files inside the v2 folder (`src/v2/tooltip/index.web.tsx`), resolved by Metro exactly as today. The duplication cost of (b) applies but only to the components actually promoted to v2.

**Testing.** Tests move or duplicate with their component. The `../../` depth change bites here: 205 cross-folder relative imports and every test's import path shift by one level for a moved component.

**Review gate.** The structurally strongest: old and new are in the same package, so the gate can be a required file (`src/v2/<name>/LEDGER.md` or a header comment) listing every ledger line as preserved-with-pointer or struck-with-reason, reviewed against the sibling file. This is Primer's `src/drafts` pattern, and Primer's promotion checklist is a ready-made script for it.

## Option (d) — token-first with targeted rewrites

**Mechanics.** Two moves, in order. (1) `apps/main/global.css` — the `@theme` scale block and the per-theme `@variant` blocks in `@layer theme`; add the scale axis from #284 as runtime variables. (2) The shared `cva` defaults in four files — `input/index.tsx:39`, `button/index.tsx:117`, `select/index.tsx:126,143,303`, `combobox/combobox.tsx:136` — which is where the audit's headline defect lives (all four default to `h-10` = 40 native units against a 44 pt floor; `sm`/`compact` are `h-9` = 36). Only then, per component and only where the mockup concordance (#337) says the *behaviour* changed, a rewrite — which can be in place (a) or behind `src/v2/` (c), decided per component.

**The ledger.** Lines **stay** for every component that only changes tokens — which the audit says is most of them ("mostly a change of shared defaults plus a states pass, not a rewrite"). Nothing moves, nothing copies, nothing is silently lost. The ledger only comes into play for the components that get a rewrite, and then under whichever of (a)/(c) that component uses. This is the option with the smallest ledger exposure by a wide margin.

**Coexistence.** A token change is global and instantaneous — same as (a), but the blast radius is a *value*, not a structure, so a wrong value is one commit to revert rather than 58 files to unpick. Scale and theme values are live knobs at runtime on both platforms (#284's finding: Tailwind v4 keeps `var(--spacing)`, `var(--text-*)`, `var(--radius-*)` in the compiled style and Uniwind resolves `var()` at runtime on native), so a token pass is a re-render, not a remount, and can even be A/B'd behind a theme. Register PRs #268–#274 need no edit; they inherit the tokens.

**Release cut.** Low risk on the token pass — the values ship as a set and can be reverted as a set. The per-component rewrites inherit the risk profile of whichever mechanism they use.

**Platform splits.** Untouched. This is the only option where the nine split files need not be opened at all for the bulk of the work.

**Testing.** The 42 tests keep running unchanged; the ones that assert class strings (`tabs-list`, `select/trigger`, `badge`) are the only ones a defaults change can redden, and those assertions are the gate working. **What is missing is a test that would catch a token regression at all** — there is no visual or token snapshot in the package today, which is what the gallery (#282's "not yet specified") is for.

**Review gate.** For the token pass the gate is not per-component at all — it is one diff of `global.css` plus four `cva` defaults, reviewed against the token sheet. The per-component ledger gate only fires on the rewrite list, which the concordance sizes.

## How others did it

- **shadcn/ui** distributes code you own, so its restyles are migrations of *your* copies. For Tailwind v4 it published a manual upgrade path — move `:root`/`.dark` out of `@layer base`, switch to `@theme inline`, drop the `hsl()` wrappers, replace `w-* h-*` with `size-*`, remove `forwardRef` — leaning on third-party codemods (Tailwind's `@tailwindcss/upgrade@next`, React's `remove-forward-ref`) rather than shipping its own, and it introduced a `data-slot` attribute on every primitive as the new styling seam ([ui.shadcn.com/docs/tailwind-v4](https://ui.shadcn.com/docs/tailwind-v4)). For the one pure restyle — the March 2025 dark-mode colour update — the prescribed path is `pnpm dlx shadcn@latest add --all --overwrite` with the blunt warning "The CLI will overwrite your existing components… Review and re-apply any changes you made to your components" ([same page](https://ui.shadcn.com/docs/tailwind-v4)). That is exactly the hard-won-customisation loss Paul is worried about, stated by the library's own authors. Where a change is mechanical, shadcn now ships a codemod instead — `pnpm dlx shadcn@latest migrate cn`, which "rewrites imports, replaces `twMerge(clsx(...))` calls and removes the old packages", under the banner "Nothing breaks" ([ui.shadcn.com/docs/changelog/2026-09-cn](https://ui.shadcn.com/docs/changelog/2026-09-cn)).
- **react-native-reusables** — our nearest neighbour ("Bringing shadcn/ui to React Native", Nativewind/Uniwind, [github.com/founded-labs/react-native-reusables](https://github.com/founded-labs/react-native-reusables)) — has done both of the things on our table. Its August 2025 "Total Rewrite" was a restyle in place at the registry level: "React Native Reusables now follows the shadcn/ui **new-york** style" and "Every component has been refined and standardized… Improved platform-specific logic" — no versioned side-by-side, consumers re-add and re-apply. Its December 2025 Uniwind support is the *parallel-variant* pattern instead: "When using the `add` command, the CLI will automatically add the Uniwind version of components when it detects a `uniwind-types.d.ts` file in your project" ([docs/changelog.mdx](https://github.com/founded-labs/react-native-reusables/blob/main/apps/docs/content/docs/changelog.mdx)) — two implementations of each component in one registry, selected by an environment probe, which is option (c) with the switch made automatic. Its theming doc is also a warning about a pattern we do not have: a `theme.ts` mirror of the CSS variables that must be hand-synced ("If you update a CSS variable, update `theme.ts` as well", [docs/customization.mdx](https://github.com/founded-labs/react-native-reusables/blob/main/apps/docs/content/docs/customization.mdx)). WCPOS has no such mirror, which is why option (d) is cheap here.
- **Uniwind** documents theming as CSS-only: "CSS-first theming with `@theme`, dark mode, custom colors, and dynamic theme switching — no ThemeProvider needed" ([docs.uniwind.dev/theming/basics](https://docs.uniwind.dev/theming/basics.md)), with `setTheme` for switching and `updateCSSVariables` to "dynamically update CSS variables at runtime for a specific theme" ([docs.uniwind.dev/theming/update-css-variables](https://docs.uniwind.dev/theming/update-css-variables.md)); scoped subtrees via `ScopedTheme` and `ScopedVariables` ([api/scoped-themes](https://docs.uniwind.dev/api/scoped-themes.md), [api/scoped-variables](https://docs.uniwind.dev/api/scoped-variables.md)). Its index has **no `cva` or variant-authoring API** — the closest are data selectors and (Pro) group variants ([docs.uniwind.dev/llms.txt](https://docs.uniwind.dev/llms.txt)). So `cva` stays our own convention, and the token layer is the only part of the system the framework itself supports moving.
- **Primer React** is the reference implementation of option (c): "New replacement components are typically built in a parallel bundle to avoid breaking existing components, and are promoted to the main bundle when it's time for migration" — source under `src/drafts`, exported as `import { ActionList } from "@primer/react/drafts"`, folder named `ActionList2` to keep the consumer-facing name, and on promotion v1 moves to `src/deprecated` and `@primer/react/deprecated`, its tests to `src/__tests__/deprecated`, its stories and docs relabelled "(legacy)", with codemods offered from a separate migration repo ([primer/react contributor-docs/deprecating-components.md](https://github.com/primer/react/blob/main/contributor-docs/deprecating-components.md)). The cost is the checklist: seven source/story/test/doc moves per component, plus a major release to flip the default.
- **Polaris** shows what a token-first redesign actually consists of. Of the 47 codemods in `@shopify/polaris-migrator`, **32 are custom-property or SCSS token replacements** (`v9-scss-replace-color`, `v11-styles-replace-custom-property-motion`, `v12-styles-replace-custom-property-space`, `v14-styles-replace-custom-property-text`, …), four more are `v9-styles-tokenize-*`, and only four are version-specific component rewrites (`v10-react-replace-text-components`, `v12-react-update-button-component`, `v12-react-avatar-component`, `v11-react-update-page-breadcrumbs`) ([Shopify/polaris-react-archive/polaris-migrator/src/migrations](https://github.com/Shopify/polaris-react-archive/tree/main/polaris-migrator/src/migrations)). And the migrator does not pretend to be complete: when it cannot transform an expression it inserts the literal comment `polaris-migrator: Unable to migrate the following expression. Please upgrade manually.` ([src/utilities/constants.ts](https://github.com/Shopify/polaris-react-archive/blob/main/polaris-migrator/src/utilities/constants.ts)) — a mechanical, greppable record of every place a human must look, which is precisely the shape the ledger gate wants.
- **MUI v4→v5** is the negative evidence for the sibling package. MUI did **not** ship two component libraries side by side; it shipped codemods (`npx @mui/codemod@latest v5.0.0/preset-safe`, plus `variant-prop` and `link-underline-hover`) and let only the *styling engine* coexist — you "may continue to use JSS for adding overrides… (for example `makeStyles`, `withStyles`)" through the explicitly deprecated `@mui/styles` bridge, then migrate off it ([mui.com/material-ui/migration/migration-v4](https://mui.com/material-ui/migration/migration-v4/)). The layer they allowed to straddle the migration was the styling layer, not the component layer.

## Recommendation

**Take (d) token-first, and reserve (c) — `src/v2/<name>` inside `packages/components` — for the named minority of components whose behaviour changes.** Do not create a sibling package.

Reasons, in order of weight:

1. **(d) is the only option that moves no ledger lines.** 262 lines, 58 components; a token pass touches `global.css` and four `cva` defaults and leaves every documented fix in the file that documents it, with its git history intact. The cohesion audit's own conclusion is that the overhaul is "mostly a change of shared defaults plus a states pass, not a rewrite", and its list of things not to touch (the semantic colour pipeline, the `Text` base-plus-context mechanism, the icon family and its 8 sizes, the HStack/VStack gap mapping, the shared `ErrorBoundary`) is the top of the census — `text`, `icon`, `hstack`, `vstack`, `error-boundary` are 902 of 1,988 imports and 7 ledger lines between them. The most expensive components to change are the ones the audit says are already right.
2. **Polaris is the closest precedent to what we are actually doing, and 32 of its 40 migrations were token replacements.** A redesign over an existing library, without a fork, was overwhelmingly a token job with four component rewrites.
3. **(b) costs the most and buys the least here.** Six config edits plus a workspace package, one of them in `apps/main/package.json` (a native-fingerprint input, so potentially a metered EAS build), duplicated platform splits, duplicated tests, and — the decisive one — a copied file starts a fresh git history, which is exactly how the ledger already lost `collapsible`'s past. Its one genuine advantage, a clean release cut mid-migration, is matched by (c).
4. **(c) is free to adopt in this repo and can be adopted per component, later.** Every resolver already maps the namespace by wildcard to `src/`, `@source` already globs `src/**`, and `lib/`, the primitives and the platform files are shared by construction. There is no reason to pay for it up front and no penalty for reaching for it on the day a component needs it. Primer's checklist is the promotion script when one does.
5. **(a) is the fallback for the thin-ledger, high-usage components** — `vstack`, `hstack`, `suspense`, `card`, `list-item`, `badge` and the fourteen used from fewer than three files. Restyling those in place is a smaller diff than any v2 ceremony, and there is no ledger to lose.

**Concretely, the order of work:** (i) land the token sheet — the scale axis from #284 and the recalibrated themes — in `apps/main/global.css`; (ii) fix the shared control core in the four files the audit names (`h-10`/`h-9` → the 44 pt floor, radius family), which is one reviewable diff that repaints Input, Button, Select and Combobox everywhere at once; (iii) take the states pass per component in place; (iv) from the concordance (#337), name the components whose behaviour changes, and open `src/v2/<name>` only for those, each with a preserved-or-struck ledger sheet beside it; (v) drop `data-table`, `tree-select` and `toggle`'s dead exports with a one-line note each.

**What would change my mind.** If the concordance (#337) comes back saying more than roughly a dozen components change *behaviour*, not skin — different composition, different props, a different interaction model — then (d)'s premise is wrong, the work is a rebuild rather than a restyle, and (c) should be the default with (d) as the first step inside it. If Paul wants the new language shipped screen-by-screen with a visible rollback per screen (a merchant-facing beta), (b)'s clean boundary starts to earn its cost — but even then I would build it as `src/v2/` first and extract a package only if the boundary proves it needs to be enforced by the module system. And if the 44 pt floor turns out to need per-component geometry rather than one shared default, step (ii) fragments and the token-first lever is weaker than the audit suggests.

## Open risks

- **The ledger is the only record, and it is on a research branch.** Under (d) most lines never move, but nothing in the repo connects a line to the code it describes. Before any rewrite starts, the ledger should exist where the code is — a `LEDGER.md` per rebuilt component, or a required section in the component's own file — or the preserved-or-struck gate has nothing to check against. Memory's own rule applies: a lesson is not learned until it is in the repo.
- **Token-first has no regression instrument.** There is no visual or token snapshot in `packages/components` today, and the one place a wrong value shows up is a screen. Step (i) should not land before the gallery (#282, "not yet specified") can shoot it, or the first evidence of a bad token will be Paul's device.
- **A restyle can preserve a ledger line's text while destroying its behaviour.** The `button/index.tsx` Android `disabled` fix (monorepo#1614) is the archetype: the comment survives any rewrite of the surrounding Pressable, the behaviour does not. Nine of the components with the deepest ledgers have *no* test covering the ledgered behaviour. Where a line is load-bearing and untested, the rebuild ticket should add the test before the restyle, not after.
- **Platform splits are barely tested.** jsdom jest has no platform-extension resolution (`packages/core/jest.config.js:71`), so only four of the nine `.web` files are exercised at all, and only by tests that import them literally. Any option that copies or moves those files is copying untested code.
- **The uniwind pin is still wrong on `next`.** `package.json` asks for `1.11.0`, `pnpm-lock.yaml` resolves `1.10.1`; `ScopedVariables` is 1.11.0-only (#284). The token sheet's scale axis depends on resolving this, and it is not this ticket's to fix.
- **`packages/components` is hot.** 106 commits since 2026-08-01, including four overlay batches in September. Any option that rewrites those files fights merge conflicts with in-flight behaviour fixes; any option that copies them will silently miss the fixes landing while the copy is in progress.
- **Census caveats.** Counts are lexical: they include test files and `jest.mock()` calls, and they miss components reached indirectly (`FormCombobox` re-exports `combobox` through `@wcpos/components/form`, so `combobox`'s real reach is larger than 35). `apps/electron` is not in this repo, so its usage is uncounted; if it imports the package from its own clone, the blast radius is larger than this table.
