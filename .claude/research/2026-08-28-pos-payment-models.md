# Prior-art POS payment models — Medusa, Square, Shopify, Odoo, Adyen

Research for roadmap#98. Facts and citations only; no recommendations. Primary sources only (official API references, docs, source code), read 2026-08-28. Anything I could not follow to a source is marked **unverified**. Stripe Terminal is included as a sixth source because roadmap#97 §5 flags a Stripe-specific claim "verify in R2".

## 1. Comparison

| | Method/tender object | Payment object | Status vocabulary | Split | Cash tendered / change | Offline | Refund model | Receipt fields retained |
|---|---|---|---|---|---|---|---|---|
| **Medusa v2** | `PaymentProvider` — id + `is_enabled` only | `PaymentCollection` → `PaymentSession` → `Payment` → `Capture`/`Refund` | on the **collection** (8) and **session** (7); `Payment` has **no status** | N sessions per collection; `partially_authorized` | **not modelled** | not modelled | `Refund` rows + `RefundReason`; hard-capped at captured | opaque `data` JSONB only |
| **Square** | `Tender` on the Order, 10 `type`s | `Payment` (7 `source_type`s); `Tender.id` **is** the payment id | `Payment.status` 5; `TenderCardDetails.status` 4; `PaymentRefund.status` 4 | authorize N (`autocomplete:false`) then `PayOrder` | **first class**: `buyer_tendered_money` / `buyer_supplied_money` + derived `change_back_money` | `is_offline_payment` + `offline_payment_details.client_created_at`; queued payments have no id | `PaymentRefund` with **`unlinked`** (no original payment) + `destination_type` | `receipt_number` (4 chars), `receipt_url`, EMV `auth_result_code` / `application_*` |
| **Shopify** | none — `gateway` is a display **string** | `OrderTransaction[]`, append-only, `parentTransaction` chain | `kind` 8 × `status` 6; order `displayFinancialStatus` 8 | N transactions on one order | change is a transaction **`kind: CHANGE`**; rounding at order level | merchant feature; **no API surface (unverified)** | `Refund` w/ `transactions[]`; destination capped per method by policy | `receiptJson` (gateway JSON) + `CardPaymentDetails` |
| **Odoo POS** | **`pos.payment.method`** — a real config record | `pos.payment` rows on `pos.order` | `payment_status` is a free-text `Char` (11 observed values) | N `pos.payment` rows per order | change is a **negative cash row**, `is_change=True`; order `amount_return` | IndexedDB queue; client-minted `uuid` with a unique constraint | refund = a **new `pos.order`** with negated lines | `ticket` (Char), `card_brand`, `card_no`, `payment_method_authcode`, `transaction_id` |
| **Adyen Terminal** | none — the terminal is the method | `PaymentRequest` / `PaymentResponse` message pair | `Result` 3 (`Success`/`Failure`/`Partial`) + `ErrorCondition` 17 | `SplitPaymentFlag`+`PaidAmount`; separately partial auth | only `CashBackAmount`; **no tender/change** | store-and-forward on the terminal; degraded response shape | referenced (`ReversalRequest`) vs **unreferenced** (`PaymentType: Refund`) | `PaymentReceipt[]` — **rendered print lines**, not fields |

## 2. Per-system notes

### Medusa v2

Four-level chain: `PaymentCollection` (`amount`, `authorized_amount`, `captured_amount`, `refunded_amount`, `completed_at`, `status`) → `PaymentSession` (`amount`, `provider_id`, `data`, `context`, `status`, `authorized_at`) → `Payment` (`amount`, `provider_id`, `data`, `captured_at`, `canceled_at`) → `Capture`/`Refund` (`amount`, `created_by`; `Refund` adds `refund_reason` + `note`) — [payment-collection.ts](https://github.com/medusajs/medusa/blob/develop/packages/modules/payment/src/models/payment-collection.ts), [payment-session.ts](https://github.com/medusajs/medusa/blob/develop/packages/modules/payment/src/models/payment-session.ts), [payment.ts](https://github.com/medusajs/medusa/blob/develop/packages/modules/payment/src/models/payment.ts), [refund.ts](https://github.com/medusajs/medusa/blob/develop/packages/modules/payment/src/models/refund.ts).

- **`Payment` carries no status field** — state derives from `captured_at`/`canceled_at` plus the `captures[]`/`refunds[]` sums; authoritative status lives on the session ([common.ts](https://github.com/medusajs/medusa/blob/develop/packages/core/types/src/payment/common.ts)). `payment.ts` carries a source TODO proposing the `Payment` model be deleted in favour of `PaymentSession`.
- `PaymentCollectionStatus` = `not_paid`, `awaiting`, `authorized`, `partially_authorized`, `canceled`, `failed`, `partially_captured`, `completed` ([src](https://github.com/medusajs/medusa/blob/develop/packages/core/utils/src/payment/payment-collection.ts)). `PaymentSessionStatus` = `authorized`, `captured`, `pending`, `requires_more`, `error`, `canceled`, `pending_authorization` ([src](https://github.com/medusajs/medusa/blob/develop/packages/core/utils/src/payment/payment-session.ts)). Three collection statuses (`partially_captured`, `failed`, `canceled`) are declared but assigned nowhere in the module — reserved-but-dead ([payment-module.ts](https://github.com/medusajs/medusa/blob/develop/packages/modules/payment/src/services/payment-module.ts)).
- **Provider interface**: `initiatePayment`, `updatePayment`, `deletePayment`, `authorizePayment`, `capturePayment`, `refundPayment`, `retrievePayment`, `cancelPayment`, `getPaymentStatus`, `getWebhookActionAndData`, `getIdentifier` ([provider.ts](https://github.com/medusajs/medusa/blob/develop/packages/core/types/src/payment/provider.ts)). Only `authorizePayment` and `getPaymentStatus` must return a status; capture/refund/cancel return `{ data }` only. Errors are thrown — `PaymentProviderError` no longer exists.
- **Manual lane**: the built-in `system` provider authorizes immediately with no external call and no-ops capture/refund/cancel ([system.ts](https://github.com/medusajs/medusa/blob/develop/packages/modules/payment/src/providers/system.ts)); docs call it "similar to a cash-on-delivery (COD) payment method" ([docs](https://docs.medusajs.com/resources/commerce-modules/payment/payment-provider)).
- **Split**: "The payment collection supports multiple payment sessions and payments… accept payments in increments or split payments across payment providers" ([docs](https://docs.medusajs.com/resources/commerce-modules/payment/payment-collection)). `PaymentSession.payment` is `hasOne`, so splitting is N sessions, not N payments per session.
- **Guards**: capture and refund run under `SELECT … FOR UPDATE` with a 3 s lock timeout; "You cannot refund more than what is captured on the payment" (payment-module.ts L780-850, L969-1035).
- **Receipts**: no receipt model. The only retention surface is the opaque `data` JSONB on session and payment — "unstructured data returned from the payment provider… content will vary between providers" ([abstract-payment-provider.ts](https://github.com/medusajs/medusa/blob/develop/packages/core/utils/src/payment/abstract-payment-provider.ts)).
- **Cash/change: absent.** No `cash`, `tender` or `change` identifier anywhere under `packages/modules/payment/src`.

### Square

- **`Tender`** on the Order: `id` ("It is the associated payment ID"), `amount_money` (includes `tip_money`), `tip_money`, `processing_fee_money`, `type`, `card_details`, `cash_details`, `payment_id`, `note` ([Tender](https://developer.squareup.com/reference/square/objects/Tender)). `TenderType` = `CARD`, `CASH`, `THIRD_PARTY_CARD`, `SQUARE_GIFT_CARD`, `NO_SALE`, `BANK_ACCOUNT`, `WALLET`, `BUY_NOW_PAY_LATER`, `SQUARE_ACCOUNT`, `OTHER` ([enum](https://developer.squareup.com/reference/square/enums/TenderType)).
- **Cash is first class**: `TenderCashDetails.buyer_tendered_money` ("total amount of cash provided by the buyer, before change is given") + `change_back_money` ([ref](https://developer.squareup.com/reference/square/objects/TenderCashDetails)); the Payment-side twin is `CashPaymentDetails.buyer_supplied_money` + a **read-only, derived** `change_back_money` ([ref](https://developer.squareup.com/reference/square/objects/CashPaymentDetails)).
- **Manual / "taken elsewhere" lane** lives on the Payment, not the Tender: `source_type = EXTERNAL` + `ExternalPaymentDetails{type, source, source_id, source_fee_money}`, `type` ∈ `CHECK`, `BANK_TRANSFER`, `OTHER_GIFT_CARD`, `CRYPTO`, `SQUARE_CASH`, `SOCIAL`, `EXTERNAL`, `EMONEY`, `CARD`, **`STORED_BALANCE`** ("Use for house accounts, store credit, and so forth"), `FOOD_VOUCHER`, `OTHER` ([ref](https://developer.squareup.com/reference/square/objects/ExternalPaymentDetails), [docs](https://developer.squareup.com/docs/payments-api/take-payments/external-payments)). There is **no `TenderExternalDetails` object** (404); what `Tender.type` an external payment surfaces as is unverified.
- `Payment.status` = `APPROVED`, `PENDING`, `COMPLETED`, `CANCELED`, `FAILED`; `source_type` = `CARD`, `BANK_ACCOUNT`, `WALLET`, `BUY_NOW_PAY_LATER`, `SQUARE_ACCOUNT`, `CASH`, `EXTERNAL` ([Payment](https://developer.squareup.com/reference/square/objects/Payment)).
- **Receipts**: `receipt_number` (max **4** chars, "missing if a payment is canceled") and `receipt_url` ("only populated for `COMPLETED` payments"). EMV fields sit on `CardPaymentDetails`: `auth_result_code`, `application_identifier`, `application_name`, `application_cryptogram`, `verification_method`, `verification_results`, `cvv_status`, `avs_status`, `entry_method` ∈ `SWIPED`/`KEYED`/`EMV`/`ON_FILE`/`CONTACTLESS` ([ref](https://developer.squareup.com/reference/square/objects/CardPaymentDetails)).
- **Split requires a two-phase protocol**: "To apply multiple payments to an order, applications must use the Orders API (`PayOrder` endpoint). These payments must be previously authorized." — `CreatePayment` N times with `autocomplete: false`, then `PayOrder` with the ids; a lone `CreatePayment` "must match the order total". Cash is included ([pay-for-orders](https://developer.squareup.com/docs/orders-api/pay-for-orders)).
- **Refunds**: `PaymentRefund.status` = `PENDING`, `COMPLETED`, `REJECTED`, `FAILED`; `destination_type` ∈ `CARD`, `BANK_ACCOUNT`, `WALLET`, `BUY_NOW_PAY_LATER`, `CASH`, `EXTERNAL`, `SQUARE_ACCOUNT`; boolean **`unlinked`** flags a refund with no Square payment behind it ([ref](https://developer.squareup.com/reference/square/objects/PaymentRefund)). "Use an unlinked refund when there's no Square payment to link to (such as when the original payment was processed by another payment processor)"; a cash unlinked refund posts `destination_id: CASH` + `cash_details.seller_supplied_money` ([docs](https://developer.squareup.com/docs/refunds-api/unlinked-refunds)). Limits: 20 refunds per payment, 1 year, `COMPLETED` only; "Regardless of whether a payment is partially or fully refunded, the payment status remains `COMPLETED`" ([docs](https://developer.squareup.com/docs/payments-api/refund-payments)).
- **Offline** is API-visible but thin: `Payment.is_offline_payment` and `offline_payment_details`, which has exactly one property, `client_created_at`, on a page marked **Deprecated** ([ref](https://developer.squareup.com/reference/square/objects/OfflinePaymentDetails)). SDK side: payments are "stored (queued) locally on the mobile device"; `processingMode` ∈ `ONLINE_ONLY`/`OFFLINE_ONLY`/`AUTO_DETECT`; `OfflinePayment.status` ∈ `QUEUED`, `UPLOADED`, `FAILED_TO_UPLOAD`, `FAILED_TO_PROCESS`, `PROCESSED`; "the transaction isn't returned from the `ListPayments` endpoint and doesn't have a Square payment ID value"; up to 1000 payments for 24 h ([docs](https://developer.squareup.com/docs/mobile-payments-sdk/android/offline-payments)).
- **Idempotency**: required `idempotency_key` on `CreatePayment` (max 45), `RefundPayment` (45), `CreateTerminalCheckout` (64); replaying a key returns the first response, changing the body under it errors ([docs](https://developer.squareup.com/docs/build-basics/common-api-patterns/idempotency)).
- **Terminal**: `TerminalCheckout.status` = `PENDING`, `IN_PROGRESS`, `CANCEL_REQUESTED`, `CANCELED`, `COMPLETED`, with `payment_ids[]` and `cancel_reason` ∈ `BUYER_CANCELED`/`SELLER_CANCELED`/`TIMED_OUT` ([ref](https://developer.squareup.com/reference/square/objects/TerminalCheckout)). `TerminalRefund` "**Only supports Interac** (Canadian debit network) payment refunds" ([ref](https://developer.squareup.com/reference/square/objects/TerminalRefund)).

### Shopify

- **An append-only transaction ledger, not a tender table.** `OrderTransaction`: `kind`, `status`, `gateway`, `formattedGateway`, `amountSet`, `paymentDetails`, `paymentIcon`, `receiptJson`, `authorizationExpiresAt`, `manuallyCapturable`, `multiCapturable`, `parentTransaction`, `totalUnsettledSet`, `errorCode`, `paymentId`, `accountNumber`, `user` (the POS staff member) ([ref](https://shopify.dev/docs/api/admin-graphql/latest/objects/OrderTransaction)).
- `OrderTransactionKind` = `AUTHORIZATION`, `CAPTURE`, `SALE`, `VOID`, `REFUND`, **`CHANGE`** ("The money returned to the customer when they've paid too much during a cash transaction"), **`EMV_AUTHORIZATION`**, `SUGGESTED_REFUND` ([enum](https://shopify.dev/docs/api/admin-graphql/latest/enums/OrderTransactionKind)). `OrderTransactionStatus` = `PENDING`, `SUCCESS`, `FAILURE`, `ERROR`, `AWAITING_RESPONSE`, `UNKNOWN` ([enum](https://shopify.dev/docs/api/admin-graphql/latest/enums/OrderTransactionStatus)). REST exposes narrower five- and four-value sets ([REST](https://shopify.dev/docs/api/admin-rest/2024-04/resources/transaction)).
- **Change is a ledger row, not a field**; there is no "amount tendered" field on Order or Transaction — it is reconstructable only as `SALE` + `CHANGE`. Cash rounding *is* explicit: `Order.totalCashRoundingAdjustment` typed `CashRoundingAdjustment` with separate `paymentSet`/`refundSet` ([ref](https://shopify.dev/docs/api/admin-graphql/latest/objects/CashRoundingAdjustment)), plus transaction-level `amount_rounding` "The rounding adjustment for cash payments" (REST).
- **Method identity is a display name.** `Order.paymentGatewayNames` is "a list of the names of all payment gateways used for the order. For example, 'Shopify Payments' and 'Cash on Delivery (COD)'" ([Order](https://shopify.dev/docs/api/admin-graphql/latest/objects/Order)). Cash and custom tenders are admin-configured **manual payment methods**, reserved names Bank Deposit, Cash, COD, Gift Card, Money Order, Store Credit ([help](https://help.shopify.com/en/manual/payments/manual-payments)). The machine gateway strings are **unverified** — no official page enumerates them, and no Admin API endpoint lists a store's configured POS tenders (**unverified**). A separate read-only `TenderTransaction.payment_method` *does* have a closed vocabulary: `credit_card`, `cash`, `android_pay`, `apple_pay`, `google_pay`, `samsung_pay`, `shopify_pay`, `amazon`, `klarna`, `paypal`, `unknown`, `other` ([ref](https://shopify.dev/docs/api/admin-rest/2024-04/resources/tendertransaction)).
- **Split**: "You can accept more than one payment method for an order by tapping Split payment…" ([help](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/payment-management/multiple-partial-payments)) — N transactions on the order.
- **Refunds** carry `transactions[]` and a two-step protocol: `calculate` returns `kind: "suggested_refund"` which "must be changed to `"kind" : "refund"` for the refund to be accepted" ([ref](https://shopify.dev/docs/api/admin-rest/latest/resources/refund)). Destination discipline is policy: "The amount that a customer paid with a payment method is the maximum that you can refund with that payment method"; "Orders paid with a custom payment method can only be refunded with the custom payment method" ([help](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/order-management/complete-refund-orders)).
- `displayFinancialStatus` = `PENDING`, `AUTHORIZED`, `PARTIALLY_PAID`, `PAID`, `PARTIALLY_REFUNDED`, `REFUNDED`, `VOIDED`, plus GraphQL-only `EXPIRED` ([enum](https://shopify.dev/docs/api/admin-graphql/latest/enums/OrderDisplayFinancialStatus)).
- **Offline** is documented merchant-side only — "Offline transactions aren't routed to the payment processor. You might not know that a transaction has failed until you reconnect"; merchants set a device daily limit and a per-order transaction limit ([help](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/selling-offline/offline-payments)). Whether an offline sale is distinguishable in the Admin API is **unverified**.
- `receiptJson` is typed `JSON` and gateway-shaped; the docs give it **no prose definition** — REST `receipt` appears only in examples (`{"testcase": true, "authorization": "123456"}`).

### Odoo POS (source read on branch `18.0`)

- **`pos.payment.method` is a first-class merchant-config record** — the closest prior art to a descriptor: `name` (translatable), `sequence`, `active`, `image`, `journal_id`, `outstanding_account_id`, `receivable_account_id`, `config_ids` (which registers may use it), `company_id` ([src](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/point_of_sale/models/pos_payment_method.py)).
  - `type` is **computed, not authored**: `cash`/`bank` from `journal_id.type`, else `pay_later`; `is_cash_count = (type == 'cash')`.
  - `payment_method_type` ("Integration") ∈ `none`, `terminal`, `qr_code` — the capture-mode axis, separate from `type`.
  - `use_payment_terminal` is a Selection whose **base value list is empty**; each terminal module appends its key: `stripe`, `adyen`, `six`, `viva_wallet`, `razorpay`, `mercado_pago`, `paytm`, `pine_labs` (`addons/pos_<name>/models/pos_payment_method.py`, same branch).
  - `split_transactions` is **not** about split tenders: "Forces to set a customer when using this payment method and splits the journal entries for each customer" (labelled *Identify Customer*).
- **`pos.payment`** rows hang off `pos.order.payment_ids` (One2many): `amount`, `payment_method_id`, `payment_date`, `currency_id`/`currency_rate`, `partner_id`, `session_id`, `card_type`, `card_brand`, `card_no` ("Card Number(Last 4 Digit)"), `cardholder_name`, `payment_ref_no`, `payment_method_authcode` ("Payment APPR Code"), `payment_method_issuer_bank`, `payment_method_payment_mode`, `transaction_id`, `payment_status`, `ticket` ("Payment Receipt Info"), `is_change`, `account_move_id`, and a `uuid` with a **unique SQL constraint** ([src](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/point_of_sale/models/pos_payment.py)).
- **Change is a negative cash payment row.** `_process_payment_lines` writes `{'name': _('return'), 'amount': -amount_return, 'payment_method_id': <first is_cash_count>, 'is_change': True}` and raises "No cash statement found for this session. Unable to record returned cash." if none exists; the order's `amount_return` is derived by negating the negative rows ([pos_order.py](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/point_of_sale/models/pos_order.py)).
- **Rounding** is `pos.config.cash_rounding` + `only_round_cash_method` + a `rounding_method` → `account.cash.rounding` with `rounding` (smallest coinage), `rounding_method` ∈ `UP`/`DOWN`/`HALF-UP`, `strategy` ∈ `biggest_tax`/`add_invoice_line` — POS accepts only `add_invoice_line` ([src](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/account/models/account_cash_rounding.py), [docs](https://www.odoo.com/documentation/18.0/applications/sales/point_of_sale/pricing/cash_rounding.html)). Source carries an open `# TODO: add support for mix of cash and non-cash payments when both cash_rounding and only_round_cash_method are True`.
- **Offline**: an IndexedDB queue in `data_service.js` (`network.unsyncData`, `syncData()` with a per-item retry counter, a `browser.addEventListener("offline")` flip); rows are created server-side on sync and de-duplicated by the client-minted `uuid` ([src](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/point_of_sale/static/src/app/models/data_service.js)).
- **Refund = a new order.** `_prepare_refund_values` negates the totals, sets `amount_paid: 0` and a fresh `uuid`; the link (`refunded_order_id`, `refund_orders_count`) is computed from refunded order lines. Terminal-side reversal is `send_payment_reversal(uuid)`, gated on `supports_reversals` ([payment_interface.js](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/point_of_sale/static/src/app/payment/payment_interface.js)).
- **`payment_status` is a free-text `Char`**, not an enum. Values written by core and drivers: `waiting`, `waitingCard`, `waitingCapture`, `waitingCancel`, `pending`, `retry`, `timeout`, `reversing`, `reversed`, `done`, `force_done`. An **empty** status is the marker for a non-electronic tender: `is_electronic() { return Boolean(this.get_payment_status()); }` ([pos_payment.js](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/point_of_sale/static/src/app/models/pos_payment.js)).
- **Receipt**: `ticket` is *appended to* by the driver via `set_receipt_info(value)`; the interface docstring instructs "You should also set `card_type` and `transaction_id` on the line". `export_for_printing()` emits `{amount, name, ticket}`.

### Adyen POS / Terminal API

Adyen's implementation of the nexo Retailer Protocol ([docs](https://docs.adyen.com/point-of-sale/design-your-integration/terminal-api)). It is a **message protocol, not a data model** — no persisted payment or method object. Enum values below were read from the official [OpenAPI spec](https://raw.githubusercontent.com/Adyen/adyen-openapi/main/json/TerminalAPI-v1.json).

- Envelope: `SaleToPOIRequest` = `MessageHeader` + one body. Header requires `MessageClass`, `MessageCategory` (20 values incl. `Payment`, `Reversal`, `TransactionStatus`, `StoredValue`), `MessageType`, `SaleID`, `POIID`; `ServiceID` must be 1–10 alphanumeric chars **unique within 48 h per terminal** ([docs](https://docs.adyen.com/point-of-sale/basic-tapi-integration/make-a-payment)).
- `PaymentRequest` = `SaleData` (`SaleTransactionID{TransactionID, TimeStamp}`, `SaleReferenceID`, `OperatorID`, `SaleToAcquirerData`) + `PaymentTransaction` (`AmountsReq`: `Currency`, `RequestedAmount`, `TipAmount`, `CashBackAmount`, `PaidAmount`, `MinimumSplitAmount`) + optional `PaymentData` (`PaymentType` ∈ `Normal`, `Refund`, `CashAdvance`, `CashDeposit`, `PaidOut`, `Recurring`, `Instalment`, …; `SplitPaymentFlag`; `CardAcquisitionReference`). **Amounts are decimals, not minor units** (max `99999999.999999`); `SaleToAcquirerData` is a *string* (form-encoded or Base64 JSON).
- `Response.Result` ∈ `Success` | `Failure` | **`Partial`**; `ErrorCondition` has 17 values (`Aborted`, `Busy`, `Cancel`, `DeviceOut`, `InsertedCard`, `InProgress`, `LoggedOut`, `MessageFormat`, `NotAllowed`, `NotFound`, `PaymentRestriction`, `Refusal`, `UnavailableDevice`, `UnavailableService`, `InvalidCard`, `UnreachableHost`, `WrongPIN`). Adyen's explicit instruction: **code against `ErrorCondition`, not `refusalReason`/`message`** ([error-scenarios](https://docs.adyen.com/point-of-sale/error-scenarios)).
- `PaymentResult` → `PaymentInstrumentData.PaymentInstrumentType` ∈ `Card`|`Check`|`Mobile`|`StoredValue`|`Cash`; `CardData` = `PaymentBrand`, `MaskedPan`, `EntryMode` (**an array**: `RFID`, `Keyed`, `Manual`, `File`, `Scanned`, `MagStripe`, `ICC`, `SynchronousICC`, `Tapped`, `Contactless`, `Mobile`), `PaymentToken`. `PaymentAcquirerData` = `MerchantID`, `AcquirerTransactionID`, `ApprovalCode`, `HostReconciliationID`. `AmountsResp` = `AuthorizedAmount`, `TipAmount`, `CashBackAmount`.
- **`PaymentReceipt[]` is rendered print output, not fields.** Each element is `{DocumentQualifier ∈ SaleReceipt|CashierReceipt|CustomerReceipt|Document|Voucher|Journal, OutputContent{OutputFormat ∈ MessageRef|Text|XHTML|BarCode, OutputText[]}}`, and each `OutputText` carries `Text` plus `CharacterStyle`, `Alignment`, `EndOfLineFlag` — a laid-out line, not a key. Adyen does publish the key catalogue that gets rendered (`authCode`, `aid`, `atc`, `pan`, `posEntryMode`, `cvmRes`, `mid`, `tid`, `rrn`, `stan`, `txdate`, `txRef`, `paymentMethod`, `cardholderName`, `sigline`, …) and warns **values are URL-encoded** ([generate-receipts](https://docs.adyen.com/point-of-sale/basic-tapi-integration/generate-receipts), [print-data](https://docs.adyen.com/point-of-sale/shopper-engagement/print-data)). The precise in-`Text` key/value layout is **unverified** — every published example is elided as `[...]`.
- **Two unrelated "split" mechanisms.** (a) *Partial authorization*: tender option `AllowPartialAuthorisation`, returns `Result: "Partial"` with `AuthorizedAmount < RequestedAmount`; **the POS must track and loop for the remainder itself** ([docs](https://docs.adyen.com/point-of-sale/partial-authorizations)). (b) *Split payments*: `SplitPaymentFlag: true` on **every** request, same `SaleTransactionID` across splits, `RequestedAmount` = still due and `AmountsReq.PaidAmount` = already paid; cash is an accepted tender inside this flow ([pay-at-x](https://docs.adyen.com/point-of-sale/pay-at-x)).
- **Refunds are two different operations.** *Referenced* = a `ReversalRequest` against `OriginalPOITransaction` with `ReversalReason` ∈ `CustCancel`|`MerchantCancel`|`Malfunction`|`Unable2Compl`; omit `ReversedAmount` for full, supply a smaller one for partial; always **asynchronous** (`Success` means "received"), outcome via the `CANCEL_OR_REFUND` webhook ([docs](https://docs.adyen.com/point-of-sale/basic-tapi-integration/refund-payment/referenced)). *Unreferenced* = a `PaymentRequest` with `PaymentType: "Refund"` — any amount to any card, enabled per device, unavailable in seven named markets, "you are fully liable"; webhook `REFUND_WITH_DATA` ([docs](https://docs.adyen.com/point-of-sale/basic-tapi-integration/refund-payment/unreferenced)). Aborting an in-flight transaction is a third operation (`AbortRequest`), and cancelling a pending unreferenced refund is a fourth (a Payment-API call, not Terminal API).
- **Offline** is store-and-forward on the terminal: "your integration approves payments before the money is received… You are fully liable." Per-transaction cap, max stored payments and supported card types are per-account values set by Adyen Support; cashback, magstripe and QR wallets are excluded; the mobile SDK is limited to 24 consecutive hours. The **response shape degrades**: `POITransactionID` carries the tender reference only (no PSP reference), `OnlineFlag: false`, `AuthenticationMethod: "OfflinePIN"`, and `PaymentAcquirerData` lacks `AcquirerTransactionID` and `ApprovalCode` ([offline-payment](https://docs.adyen.com/point-of-sale/offline-payment)).
- **Cash tendered/change: absent.** `CashBackAmount` is the only cash construct in the envelope ([cashback](https://docs.adyen.com/point-of-sale/cashback-and-cash-out)). Cash-shaped enum values exist (`PaymentInstrumentType: "Cash"`, `PaymentType: "CashAdvance"/"CashDeposit"/"PaidOut"`) but Adyen publishes no flow for recording a cash tender.
- **Unknown-outcome recovery is a first-class message**: `TransactionStatusRequest` with `MessageReference` naming the original `ServiceID` returns `RepeatedMessageResponse` containing the original `PaymentResponse` verbatim. The wrapper `Result` only says whether an end state was reached — the real outcome is the nested response. Time out first at 120 s local / 150 s cloud, then poll on `InProgress` with no client-side delay ([docs](https://docs.adyen.com/point-of-sale/basic-tapi-integration/verify-transaction-status)).

### Stripe Terminal (checked only for the roadmap#97 §5 claim)

Flow is create → collect → confirm → capture. The docs mark **create as either client- or server-side** (`createPaymentIntent` exists in the SDK), **confirm as client-side only** ("Always confirm PaymentIntents using the Terminal SDK on the client. Server-side confirmation bypasses critical interactions, such as PIN prompts"), and **capture as server-side** ([docs](https://docs.stripe.com/terminal/payments/collect-card-payment.md?terminal-sdk-platform=react-native)). Offline: the SDK stores payments locally and forwards on reconnect; while offline the `PaymentIntent` **has a null `id`**, so Stripe recommends "adding a custom identifier to the PaymentIntent's metadata to help reconcile". `offlineDetails.requiresUpload` marks an unforwarded intent, `offlineDetails.offlineCardPresentDetails` carries a `ReceiptDetails` for printing, `account_type` and `authorization_response_code` are **unavailable offline**, the ceiling is 10,000 USD, `offlineBehavior` ∈ `REQUIRE_ONLINE`/`PREFER_ONLINE`/`FORCE_OFFLINE`, a Bluetooth reader must have paired online at the same Location within 30 days, and "You can't cancel or refund a PaymentIntent that was created and confirmed offline until it's forwarded to Stripe" ([docs](https://docs.stripe.com/terminal/features/operate-offline/collect-card-payments.md?terminal-card-present-integration=terminal&reader-type=bluetooth&terminal-sdk-platform=react-native)).

## 3. Convergences

1. **Two nouns, always: a method/tender descriptor and N payment records against one order.** Every system that persists orders (Square, Shopify, Odoo, Medusa) makes split tender "N rows on one order" — **none uses sub-orders.** Adyen, which persists nothing, still threads splits with one shared sale reference.
2. **The payment row owns the money event; the order's payment state is derived** — Medusa's collection rollups, Shopify's `displayFinancialStatus`, Odoo's `amount_paid`/`amount_return`, Square's `PayOrder` completion rule.
3. **A status vocabulary in the authorize → capture → refund/void family**, always with a pending and a failure state: Square 5, Medusa session 7, Shopify `kind` × `status`, Adyen 3 results + 17 error conditions.
4. **The provider payload is retained as one opaque bag** — Medusa `data` JSONB, Shopify `receiptJson`, Square's per-`source_type` detail objects, Odoo's `ticket` plus terminal columns. Nobody normalizes provider fields into a shared schema.
5. **Receipt-bearing card fields recur almost verbatim across all five**: brand, masked PAN / last-4, entry mode, approval/auth code, and an EMV block.
6. **Every system has an explicit "no processor involved" lane** as a first-class concept, not a workaround: Medusa's `system` provider, Square's `source_type: EXTERNAL`, Shopify's manual payment methods, Odoo's `payment_method_type: none` (empty `payment_status`), Adyen's unreferenced refund.
7. **Manual and provider refunds are modelled separately** wherever both exist — Square's `unlinked` boolean and Adyen's referenced/unreferenced split are the two explicit switches.
8. **Client-minted ids are the offline idempotency device**: Odoo's `uuid` (unique SQL constraint), Stripe's "custom identifier in metadata", Square's `client_created_at` plus a required `idempotency_key`. The server-assigned id does not exist yet when the sale completes.
9. **Where cash is modelled at all it is tendered + change as a pair, with change derived** — Square's `buyer_tendered_money`/`buyer_supplied_money` + read-only `change_back_money`, Odoo's negative cash row, Shopify's `CHANGE` transaction kind.
10. **Capture mode and tender identity are separate axes** wherever both are expressed. Odoo is cleanest: `type` (cash/bank/pay_later — the accounting and reporting axis) is independent of `payment_method_type` (none/terminal/qr_code) and of `use_payment_terminal` (which driver).

## 4. Divergences and traps

- **Append-only ledger vs mutable rows.** Shopify's transactions are immutable events chained by `parentTransaction` (change is its own row); Odoo's `pos.payment` rows are mutable state; Square is a hybrid (immutable `Payment`s, `Tender` a read-only projection). This decides whether "refunded" is a status on the row or a second row.
- **Where status lives.** Medusa deliberately puts none on `Payment`. Odoo's `payment_status` is an unconstrained `Char` whose *emptiness* is load-bearing (`is_electronic()` tests truthiness). Neither is a closed enum on the payment row.
- **Split is not one mechanism.** Square requires authorize-N-then-`PayOrder` and refuses a lone payment that doesn't equal the order total; Adyen has two unrelated mechanisms, one of which obliges the POS to loop for the remainder; Shopify and Odoo just append rows.
- **"Amount tendered" is not universal.** Square stores it; Odoo and Shopify reconstruct it from the change row — lossy for "cash in drawer" reporting.
- **Cash rounding is a separate concept from change, modelled at the order/register level, not the payment**: Shopify `totalCashRoundingAdjustment` (distinct payment and refund halves), Odoo `account.cash.rounding` with an explicit `strategy` and a POS restriction to `add_invoice_line`. Odoo's own source flags mixed cash/non-cash as an open TODO.
- **Refund destination policy varies by two full steps.** Shopify caps a refund per method at what was paid on it and forbids cross-tender refunds for custom methods; Square permits unlinked refunds to cash or external with no original payment at all; Odoo's model imposes nothing; Medusa hard-caps at the captured amount under a row lock.
- **Offline degrades the payload, not just the timing.** Adyen returns no PSP reference and no approval code; Stripe returns a null `PaymentIntent.id` and omits `authorization_response_code`; Square's queued payments are absent from `ListPayments` and have no id. A schema requiring provider refs on a captured payment cannot represent an offline capture.
- **Offline also constrains later operations** — Stripe forbids cancel/refund until forwarded; Adyen and Stripe both cap offline value per transaction and in aggregate, and both lose stored payments if app storage is cleared.
- **Terminal refunds are frequently not supported.** Square's `TerminalRefund` is Interac-only; Adyen's unreferenced refund is off by default and unavailable in seven markets. "The reader can take a payment" does not imply "the reader can refund it."
- **Receipt data is either fields or rendered lines, and Adyen is the odd one out** — `PaymentReceipt` hands back laid-out print rows with alignment and style, and Adyen warns that overriding scheme-certified receipt content moves compliance liability onto the integrator.
- **Naming drifts inside a single vendor**: Square spells one concept `buyer_tendered_money` (Tender), `buyer_supplied_money` (Payment), `seller_supplied_money` (refund destination).
- **Amount representation**: Adyen amounts are decimals, against the minor-unit convention elsewhere; Medusa stores every amount twice (`amount` + `raw_amount`) for exact precision.

## 5. Against the strawman (roadmap#97 §5)

**Agrees with prior art.** Two objects — a descriptor the till lists plus N payment rows per order — is universal, and Odoo's `pos.payment.method` is a near-exact analogue of `PaymentMethodDescriptor` down to `sequence`, `active`, `image` and a per-register `config_ids` scope. Separating the tender axis from the capture axis (`kind` vs `capture.mode`/`capture.provider`) is exactly Odoo's `type` vs `payment_method_type` vs `use_payment_terminal`. `tendered`/`change` on the payment is directly precedented by Square. `provider_refs` as a free-form map and `receipt` as a retained sub-object match the universal opaque-bag plus card-field pattern; the strawman's `receipt{brand, last4, auth_code, entry_mode, emv}` is close to the intersection of Square's `CardPaymentDetails` and Odoo's card columns. A client-minted uuid as the offline idempotency key is precedented by Odoo's `uuid` constraint and Stripe's metadata recommendation. `refunds[]` nested under the payment matches Medusa and Square. A `manual` capture mode and `refunds: ('provider'|'manual')[]` match Convergences 6 and 7.

**Conflicts or added constraints.**

- **`status` as one flat enum on `Payment` is the biggest divergence.** Medusa has no status on `Payment`; Shopify splits it into `kind` × `status` over an append-only ledger; Square keeps `Payment.status` at `COMPLETED` through partial *and* full refunds and puts the card lifecycle on `card_details.status`. The strawman mixes lifecycle (`pending`/`authorized`/`captured`/`failed`/`voided`) with a refund rollup (`refunded`/`partially_refunded`) in one field — no surveyed system does that, and Square explicitly does the opposite.
- **`partial_amount: boolean` understates split.** Square requires a two-phase authorize-then-`PayOrder` protocol; Adyen has two mechanisms with different wire shapes, one returning `Result: "Partial"` and obliging the POS to loop. Split capability is a protocol shape, not a boolean.
- **`offline_recordable: boolean` likewise.** Offline changes what the payment record *can contain* (no provider refs, no approval code, no server id) and what can later be done to it (Stripe forbids cancel/refund until forwarded), and carries value caps. Square models it as two fields on the payment, not as a method capability.
- **`change_due: boolean` has no analogue** — Odoo derives the cash lane from `journal_id.type` (`is_cash_count`), Square from `TenderType: CASH`. It falls out of `kind`, and a separate boolean can contradict it.
- **`rounding` under `defaults` is placed differently everywhere.** Both systems that model cash rounding put it at register/order level with its own strategy vocabulary, not on the method descriptor; Shopify's split of the adjustment into payment vs refund halves is not expressible in `{increment, mode}`.
- **The `Refund` sub-object needs a manual/unlinked flag and a destination.** Square carries both `unlinked` and `destination_type`; Shopify enforces a per-method refund ceiling. `{id, amount, status, provider_refs}` cannot express "refunded to cash a card payment" or "refund with no original payment".
- **`voided` flattens three operations.** Adyen separates aborting an in-flight transaction, reversing a completed one, and cancelling a pending unreferenced refund; Square distinguishes cancelling an `APPROVED` payment from refunding a `COMPLETED` one.
- **The `device_sdk` note is half right and its parenthetical is now verified.** Stripe Terminal does need server-side capture and a connection-token provider, but the docs allow the `PaymentIntent` to be created **client-side** and require confirmation to be client-side. The accurate framing is not "prepare on server → collect on device → capture on server" but **"create is either; confirm is client-only; capture is server-only."**
- **A descriptor `id` that is "gateway id or POS-native id" is the norm — and Shopify shows the cost of not having a registry**: its gateway is a display *name*, no API enumerates a store's configured POS tenders (unverified), so reporting groups by string. Odoo's stable `pos.payment.method` id with orphan-safe `active` is the counter-example the strawman's "union with observed history for filters" is reaching for.
- **`kind: 'stored_value'` is precedented, but as a type on the manual lane, not a capture mode**: Square's `ExternalPaymentDetails.type: STORED_BALANCE` is documented "for house accounts, store credit, and so forth". The strawman has `stored_value` on both `kind` and `capture.mode`; Square's model does not make that distinction.
