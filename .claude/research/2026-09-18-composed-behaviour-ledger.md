## What this is

The pieces the language prototype rehosts — the cart, the register bar and panel, the open-order tabs, the
tender pane and payments, the receipt stage, the products grid, table and scanners, the data table and header
chrome, the orders list and order pane, the reports page and the closures room — do not live in
`@wcpos/components`; they live under `packages/core/src/screens/main/**` and carry their own years of fixes.
#285 did not cover them. This file does, by the same method and the same evidence rule, so that the composed
half of the component map (#291) has a preserved-or-struck gate too.

**Scope:** 48 pieces (folders, or single files where a folder is a bag of independent hooks).
**Total ledger lines: 634.** Marked _inferred — no explicit evidence_: 5 (per the batch summaries).

## How it was produced

- Per-folder reading and history mining delegated to Codex (`gpt-6-astra`, read-only sandbox, reasoning
  effort high) from a worktree of `origin/next`, in six batches run one at a time: (1) `pos/cart`, (2)
  `pos/checkout` + `pos/columns` + `pos/contexts`, (3) `pos/products`, (4) `components/{data-table, header,
  drawer-content, navigation-area, ui-settings, customer}` + `orders`, (5) `components/{order, product}`,
  (6) `reports`. The task file each batch read is reproduced at the end of this document.
- Per folder Codex read every non-test source file, mined `git log --follow` for behaviour commits (chores,
  formatting, lint and dependency bumps skipped), read the bodies of promising commits, grepped comments for
  the reasons, and recorded test names that pin a behaviour.
- Claude spot-checked two lines against the source and the history (`pos/products` line 3 → commit
  `788d05594f` exists with that subject; `reports/closures` line 5 → `use-closure-rows.ts:58–82` does the
  normalisation described) and both held. The summary table below is computed from the batch outputs.

## What "evidence" means here

Each line cites at least one of: a commit `<hash> <date> <subject>` with the PR or issue number only where
the subject or body names one; or a verbatim code comment quoted with `file:line`; or a test name that pins
the behaviour. A line marked _(inferred — no explicit evidence)_ is Codex's reading of the code with no commit,
comment or test behind it: a hypothesis, not a finding.

## Caveats

- Nothing was run: no installs, builds, tests or devices. Every claim is a read of `origin/next` at
  `aebda38456` and its history.
- `git log --follow` on a directory follows one path; pieces that were moved wholesale (the register work of
  September 2026, the checkout column swap) show history from the move onward unless the commit body says
  more.
- Batch 6 (`reports`) uses footnote-style evidence markers (`[^closures]` and similar) for commits it cites
  repeatedly; the footnote definitions are at the end of that batch's section. Where a marker stands alone,
  the `file:line` beside it is the evidence.
- The concordance (#337) and its script addendum (#342) name which of these pieces the drawing touches; this
  file does not repeat that mapping. Read the two side by side when deciding a row of #291.
