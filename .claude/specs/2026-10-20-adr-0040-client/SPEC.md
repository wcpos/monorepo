### 1.2 Wire discipline: one strip, two seams; status is an intent (PR A)

**Constants and strip** in `sync-core/src/woo/orderWriteContract.ts`:
- `SERVER_OWNED_ORDER_FIELDS` and `SERVER_OWNED_ORDER_META_KEYS` (0.1's lists, commented "mirrors `Pos_Order_Audit::SERVER_MONEY_FIELDS` / `SERVER_MONEY_META_KEYS`; a new key joins both in one change"). `order-math/src/payments/ledger.test.ts` pins `LEDGER_META_KEY` and `PAYMENT_METHOD_INDEX_META_KEY` into the list.
- `PUSHABLE_ORDER_STATUSES = ['pos-open','pending','on-hold','cancelled'] as const` lives in **`@wcpos/sync-core`**: a wire fact the strip enforces; `sync-engine`, `query`, `core` already import this module; `sync-core` cannot import `order-math` (which re-exports it).
- `toOrderWirePayload(payload)`: aggregate strip + server-owned fields + server-owned meta entries + a non-pushable `status`. Same reference when clean.
- `orderChangesAssertIntent(changes, current?)` is false when every changed key is server-authored, server-owned, `date_modified_gmt`, a non-pushable or unchanged `status`, or a `meta_data` array whose remaining entries equal `current`'s (by key and value). Callers pass the resident payload they hold (`resident.ts:321-323`, `local-patch.ts:158`).

**Seams.** `sanitizeOutboundOrderPayload` calls `toOrderWirePayload` (enqueue, coalesce, recovery). `pushRecordMutation` (`recordPushAdapter.ts:188-205`) applies it to every `orders` payload at push time. No row written before protocol 3 reaches either seam (§1.5 parks them in their own generation).

**Status is an intent, never an echo.** A status reaches the wire only from a write whose own change set names it and changes it:
- `coalescedPayload` (`write-placement.ts:80-91`) takes `status` only from the prior or incoming payload, never the resident layer.
- `enqueueRecordWrite` (`push-record.ts:47-58`) omits `status` from an `update`; a `create` keeps it.
- Dead-letter recovery (`rebuiltRecoveryPayload`, `write-intents.ts:967-985`) takes `status` only from the recovered entry's own payload, never from the resident layer.
- Born-twice recovery (`write-intents.ts:1243-1304`) drops `status` from the discarded **create** snapshot before it merges into a successor or becomes the follow-up update; a successor's named status stays. A create's status never becomes an update intent.
- Both forms write `status` only when the cashier changed it: the cart form (`edit-order-meta/form.tsx:126-135`, its `patch` loses an unchanged `status`) and the orders form (`orders/edit/form.tsx:108-123`), which also shows `payment_method`, `payment_method_title`, `transaction_id` read-only. `OrderStatusSelect` takes `allowed`: the pushable set plus the current status, disabled when not pushable.
- Named writers that stay: reopen (`orders/use-reopen-order.ts:37`), the cart's send (`form.tsx:145-156`), void-order (`query/src/mutations/void-order.ts:85-89`).

**Server-owned meta on the resident.** `SERVER_ORDER_MONEY_META_KEYS` (`sync-core/src/pos-carrier/carrier.ts:57-63`) becomes `SERVER_OWNED_ORDER_META_KEYS` (epoch keys go, §1.6). The ack graft then adopts every server-owned key even with a successor queued (`collection-descriptors.ts:669-680`); `protectOrderMeta` (`resident.ts:319`) keeps the resident's value against any queued write. Local-only writers (§1.3's mirror, §1.5 PR B) use `patchEngineResident`.

**Failure story.** A missed non-pushable status is cleaned at both seams; a slipped server-owned key is dropped by the server and restored by the ack. No path re-sends a stale pushable status, so a note save on a till holding a stale `pending` copy of a paid order cannot reopen it. Real refusals reach the cashier through the awaited push's toast (SYNC201, server message) and Store health. A reopen refused with `wcpos_money_in_motion` names the leg (`data.payment_id` / `data.attempt_id`); the order menu's reopen reports it and offers the existing Cancel payments for that leg, never a silent local `pos-open`.

### 1.3 The money command envelope (PR A)

**Module.** `packages/query/src/commands/money-command.ts` (engine and store-local access allowed; `core` calls named commands, ADR 0033). `post` is injected (the authenticated client lives in `core`). `moneyCommandPoster({ runtime, storeDB, orderUuid, post, provenance, approval })` is a drop-in `(url, body) => Promise<{ data }>`.

**The command journal (one store for every in-flight command).** Every money command of all eight kinds, `close` included, persists its frozen envelope before anything else happens:

`MoneyCommandEntry = { orderUuid, kind, path, target, id, body, approval: { total, currency }, sentAt: string | null }`, where `id` is the `command_id` (or, for `record`, the row id), keyed `orderUuid → id`. Beside it, per order, the revision chain `{ answerRevision, answeredAt }`.

Store: a local document `money-commands` in the **store-local database** (`storeDB.getLocal/insertLocal` through `ensureLocalDocument`, `query/src/store-local/ensure-local-document.ts:12-30`), beside the sale-completion journal that already lives there (`store-local/completion-journal.ts:37-56`). Why there and not on the orders collection's local documents (the print-count stash, `write-path/engine-order-repository.ts:104-121`): the store database is named per store, not per scope generation (`database/src/database-names.ts:65`), so it is outside everything that rewrites or replaces an order. No meta merge, form save, local patch (including the non-enqueued path, `local-patch.ts:167-173`), pull, `resetForResync` (`engine-order-repository.ts:563-580`) or generation bump (§1.5, PR B's 7 → 8) can see it. It is never replicated. Pass-3 findings #3 (marker erased by a local-only patch, reset race) and #4 (generation bump drops PR A's unresolved commands) close by construction: there is no marker on the order to erase, and nothing to carry. The pass-2 marker key, its merge branch and the reset guard are deleted from the design.

**Approval.** `approval = { total, currency }` is frozen from the order at the cashier's press, **before** any provenance save or pre-flight push (the gateway path saves provenance first, `checkout/tender/use-tender-flow.ts:944-965`, then builds its deps, `checkout/payments/use-gateway-payment.ts:51-56`). It is passed explicitly: `gateway.submit(order, method, input, { approval })`, the terminal service's start input, `recordManualPayment`'s input and `closeSale`. The poster never samples it.

**Lifecycle.**
1. **Classify** the path: `orders/{id}/payments` → record; `…/payments/{uuid}/{intent|capture|void|refund}`; `…/payment-methods/{method}/{submit|cancel}`; `orders/{id}/close`. Anything else (the `status` poll, bootstraps) passes through untouched.
2. **Freeze** the body. `provenance` is added for `record, intent, capture, submit, close`: with no `_wcpos_completions` on the order it reads the till tuple `persistProvenance` stamped (no counter); with a completion history it mints `{ register_id, session_id, sale_time, sale_tz, sale_counter }` once through `nextSaleCounter` (`checkout/provenance/stamp-completion.ts:23-61`). Mint `command_id` (not for `record`). Write the entry with `sentAt: null`.
3. **Pre-flight.** Pending local work → await the explicit push (`pushRecord`). Choose the revision (below); if there is none, one forced refresh (`refreshRecordByWooId`, `record-readers/refresh-records.ts:46-57`). For `intent`, `submit` and `close`, check `approval` (total **and** currency) against the document whose stamp is the revision about to be sent (the resident, or the pre-flight push's acknowledged document). That document must have been **adopted whole**. Adoption authority holds only while `sync.revision === sync.adopted.revision` (below) and `sync.adopted.at` is later than `answeredAt`. If the chosen revision is the chain's `answerRevision`, or authority does not hold (a naked revision write since the adoption, or an adoption older than the answer), the envelope first runs one **corrective refresh** that re-adopts the document even under an equal stamp (`readopt`, below), and compares against what it adopted. If that refresh cannot adopt (protected, failed, offline), the command ends as `MoneyCommandError('revision_unavailable')` before `sentAt` and is never posted.
4. **Never dispatched is terminal.** If step 3 refuses (the push was refused, no revision, the approval differs), the entry is **deleted** and the error returned (`MoneyCommandError('order_changed' | 'revision_unavailable')`, or the push's own error): the request never left, so nothing can be on the server. The tender re-presents the order for a fresh approval.
5. **Dispatch.** Write `sentAt = now` and `sentRevision` (the revision about to be sent) to the entry and await it, **immediately before** the fetch; then post `{ ...body, command_id?, revision }`. From here a crash or a lost answer is ambiguous, and the only resolution is a re-send.
6. **Answer.**
   - **Definitive** (the entry is deleted in the same step that persists the answer's facts, never earlier): a 2xx whose row or summary the mirror has persisted; or a refusal naming this row or command: `wcpos_command_conflict`, `wcpos_order_already_paid`, `wcpos_amount_exceeds_balance`, `wcpos_invalid_transition`, `wcpos_balance_outstanding`, `wcpos_payment_in_flight`, `rest_invalid_param`. A refusal carrying `data.payment` is mirrored with that row. On a 2xx the chain becomes `{ answerRevision: data.revision, answeredAt: now }`.
   - **Not definitive** (the entry stays, `sentAt` stays): 409 `wcpos_payment_locked` (the lock was held and nothing ran, `Payments/Contract/Order_Lock.php:132-147`), any 5xx, a network error, a timeout, a non-JSON body, 401, 403.
   - **409 `wcpos_revision_stale`**: adopt `{ ...data.current, _rxdb_revision: data.currentRevision }` via `engine.adoptOrderSnapshot`. For `intent`, `submit` and `close`, check `approval` against `data.current` first; a difference, or an adoption answered `'protected'` (`engine-order-repository.ts:281-286, 390-394`), ends the command as `order_changed` (the server stored nothing for a stale fresh command, `Payments_Controller.php:428-439`, so the entry is deleted and the cashier re-approves). Otherwise re-send once with the same id and body and `currentRevision`. A second stale is not definitive.
7. **Retry is always a re-send.** Every retry, in the same process or after a restart, re-sends the entry's frozen body under its own id with the newest revision. The server replays `record` by row id, `intent` by its row id (resuming the leg), `submit` by attempt id and the other five by `command_id`, and the fingerprint excludes `revision` (`Command_Log.php:39-49`), so a re-send either replays the first delivery's outcome or runs it once. There is no resolution by reading. While an order has an entry with `sentAt` set, the tender offers no tile and no close, only **Try again** (re-send); a `wcpos_payment_locked` answer is re-sent after its `retry_after`, bounded by `RECORD_UNKNOWN_RETRY_DELAYS_MS` (§1.5).

**`close` is approved like a charge** (pass-3 #5). `close` is journaled like any command, so a close whose answer was lost, followed by another till reopening the sale and a restart, re-sends C1, which replays C1's completion and never completes the reopened sale as a fresh C2. A fresh close checks `approval` before dispatch and again after adopting a stale answer; a changed total that is still covered is refused as `order_changed` and the cashier approves the changed sale.

**Revision choice by recency.** A command sends the chain's `answerRevision`, unless the resident holds a document adopted whole **after** `answeredAt` (authority as above), in which case it sends the resident's `sync.revision`. Authority reads a new pair, `sync.adopted = { revision, at }` (`at` in local epoch ms). It marks a **full-document adoption**, not merely a revision write, and binds that adoption to the exact revision it adopted. A naked writer that replaces `sync.revision` while spreading `...sync` (`conflict-resolution.ts:380-385`, `write-drain-lane.ts:597-600`, `collection-descriptors.ts:393-399`) leaves `sync.adopted.revision` behind, so the inequality itself revokes authority; no writer needs to clear it. `sync.adopted` is written in the same write as `sync.revision` only where a whole server document is adopted: the pull's adopt path (`EngineOrderRepository.upsertMany`, `engine-order-repository.ts:278-410`, which the forced refresh also goes through), and `adoptOrderSnapshot` (`scheduler/rx-scheduler-order-fetcher.ts:399-440`, the stale path's adoption of `data.current`). It is **never** written by the 428 naked refresh (`write-drain-lane.ts:568-601`), the manual rebase graft (`conflict-resolution.ts:364-385`), or an ack that writes `currentRevision` without adopting the document (`collections/collection-descriptors.ts:364-400`, a successor queued). An ack that does adopt (`adopting` true, `:364`) writes it. So a revision without its document never certifies approval or a receipt.

**The corrective refresh re-adopts under an equal stamp.** A naked write can leave the resident stamped with the very revision the server now serves, and the pull then skips the payload (`local-work-guard.ts:107-109`). So the refresh the envelope runs for authority, and `settleMoneyCommand`'s post-answer refresh (§1.8), pass `readopt: true`. The flag goes on the refresh request (`refreshRecordByWooId`, `record-readers/refresh-records.ts:46-57`, into the `engine.require` request), through the require plane to the orders adopt path. There `EngineOrderRepository.upsertMany` skips `withoutUnchanged` (`engine-order-repository.ts:335-338`) for those ids, and so does `partitionPulledRows` (`local-work-guard.ts:127-133`) on the other lanes. The local-work guard still applies, so a protected resident is never overwritten; the envelope then refuses as above. The order schema's `sync` object takes additional properties (`collections/order-schema.ts:20`), so this is no schema change. A document fetched before a command but adopted after its answer can still win by this rule; it then costs one 409 `wcpos_revision_stale`, and the stale path above re-sends the same id: one round trip, no second money movement.

**Mirror, then refresh.** `mirrorServerOrder` is a resolver over the **latest** resident. It never replaces the ledger array, never deletes a row and never starts from the pre-command snapshot (`record-manual-payment.ts:153-154`). For each answered row:
- **absent** → insert it;
- **present** → the row is replaced **whole** or kept **whole**, never field-mixed. The answer's row replaces the resident's only when its `updated_at_gmt` is **strictly newer**, or **equal with a strictly forward row state** (`pending → authorized → captured → voided`; any live state → `failed`/`voided`; never backwards). Otherwise the resident row stays exactly as it is: amount, tip, capture time and status belong together. The server stamps `updated_at_gmt` on every content change of a leg (`Payments/Contract/Ledger.php:2049-2051, 2454`), but only to the second (`gmdate('c')`, `:2390-2391, 2463`), so an equal stamp proves nothing about order beyond the state machine.
- **after that decision, in both cases**, the row's arrays are unioned with the other snapshot's by id or key, so an allocation or an event is never lost either way: `refunds` by allocation `id` (an allocation's status only moves forward, `pending → succeeded | failed`), `events` by `t` + `message`, `provider_refs` by key (non-null wins). `refunded_amount` is recomputed from the merged `refunds`.

It writes the summary's **status only while** the resident's `sync.revision` still equals `sentRevision`, the revision the command was sent with, which the journal entry records at `markSent`. If a pull or refresh adopted a newer document in between, that document's status is already newer than the answer's, and the mirror leaves it. Then `settleMoneyCommand` runs the forced refresh. The row is never lost (two partial records whose refreshes both fail are both upserted and both stay counted), a late answer cannot erase an allocation or regress a row a newer document brought, and an older status is never written under a newer stamp, so the equal-stamp skip (`local-work-guard.ts:107-109`) cannot freeze a stale status. The resident's stamp is untouched, so the next push carries no artificial conflict.

**Call sites.** `use-record-manual-payment.ts:83`, `use-gateway-payment.ts:27`, `use-void-payments.ts:48`, the per-leg deps in `services/terminal-payments/service.ts` (`this.options.http` spread, ~443) and its capture at `:218`, and `closeSale` (§1.5): each `post` becomes `moneyCommandPoster(...)`; each mirror is followed by `settleMoneyCommand`.

**Failure story.** Lost answer, same process or after a restart: the journal re-sends the same id and body, and the server replays. `wcpos_payment_locked` while the first delivery still runs: not definitive; the next re-send replays. A crash between `sentAt` and the answer: ambiguous, so re-send. A crash before `sentAt`, or a local refusal: nothing left the till; the entry is gone and the order is re-approved. Form saves, local patches, pulls, resets and generation bumps cannot touch the journal. A provenance or pre-flight push that moved the total or currency, or a stale answer with a changed order, stops a charge or a close before it runs.

### 1.5 Offline tender and close (PR A refuses and parks; PR B queues)

**PR A — refused, never silent; nothing a protocol-2 client wrote is sent.** `next` is unreleased: a visible refusal is acceptable, a lost or replayed tender is not.
- **Rows written before protocol 3 are parked, never sent or reconciled** (Paul's ruling, §4.5). Mechanism: the repo's own pre-GA lever. `SCOPE_DATABASE_GENERATION` moves 6 → 7 (`sync-core/src/storeScopeIdentity.ts:66`) with the comment "7: protocol 3 (ADR 0040) — a protocol-2 queue is parked, never drained"; `drainable-generation.ts` becomes generation 6's schemas, which are today's (`DRAINABLE_SCHEMAS_GENERATION = 6`; no schema moved, so its recipe is today's creators); `schema-behaviour.test.ts` re-pins the digest map. A new constant `FIRST_PROTOCOL_3_SCOPE_GENERATION = 7` in `storeScopeIdentity.ts`; `drainLegacyScopeDatabase` (`legacy-scope-drain.ts`) checks it first: a drainable generation below it is **never pushed and its carts are never carried over**, but its receipt print counts are: `carryPosLocalState` (`legacy-scope-drain.ts:487-524`, the stash the drain already moves into the live orders collection) runs for it as for any drained generation, so a synchronized order already printed on this till still prints as a COPY after the re-sync (`receipt/use-receipt-document.ts:198-205`, `build-receipt-data.ts:995-996`). If that carry fails (a scope switch mid-carry, a write failure, `legacy-scope-drain.ts:510-527`), the outcome is `kept`, `retryable: true`, exactly as a failed carry is today, so the host retries it (`apps/main/lib/create-app-engine.ts:611-613, 637-659`); only the carry is retried, and protocol-2 pushes stay forbidden on every attempt. Parking becomes final only after the carry succeeded: then it classifies the old queue without opening the engine, returns `kept` with `reason: 'written-before-protocol-3'`, `retryable: false`, and the host logs it (`create-app-engine.ts:504-534`) at error with PAYMENT201 on the first attempt of a process and then daily (`reportDue`), naming the unsent count, so it sits in Store health's log and the health header's stuck list. Why this mechanism: it is the one the repo already uses for every pre-GA schema break, the old rows never enter the new queue (so no coalesce, recovery or push seam can touch them, and the three legacy findings of Codex pass 2 cannot arise), and nothing in the new database is frozen: every resident re-ingests from the server, so no order is blocked and no local reset is needed. Cost: one full re-sync per till, and a dev till's unsent open carts stay in the parked database. **Lifetime**: the parked generation-6 database is kept while it is the drainable generation (PR A). When PR B moves to generation 8 it is no longer drainable, and the post-readiness purge deletes it with its parked work (`database/src/database-names.ts:70-80`, `purge-legacy-db.ts:31-37`). That is the end of protocol-2 work on a dev till, by Paul's ruling. A marker-in-place migration was rejected: held rows in the live queue would block every later write to their orders forever.
- **Tiles.** `OFFLINE_TENDERS_QUEUE = false` in `checkout/tender/tiles.ts` (commented "ADR 0040 PR B queues offline tenders as money commands; until then a tender the server cannot hear is refused") disables manual `offline: 'record'` and device `settlesLater` tiles with the `'offline'` reason when offline or `queued-offline` (`tiles.ts:171-180`). PR B deletes it.
- **Cash.** No offline write; an offline call returns `{ kind: 'failed', reason: 'offline_unavailable' }` (CHECKOUT101 toast). A 5xx or no answer re-sends the same command after each of `RECORD_UNKNOWN_RETRY_DELAYS_MS = [1000, 3000, 9000]` (rides out a proxy restart, short enough to wait at a till); still unknown → `{ kind: 'unknown', command }`, PAYMENT201, and the journal entry (§1.3) keeps Try again on screen across restarts.
- **Zero balance → `close`.** `writeZeroBalanceCompletion` writes its line changes **without** `status` (`zero-balance-completion.ts:52-59`), then `closeSale` sends `close` with provenance: 2xx with `completion` → `complete()`; 409 `wcpos_balance_outstanding` → mirror the summary, show what is due (a zero-total sale lands here only until #2366 merges; then `close` completes it); 409 `wcpos_payment_in_flight` → name the leg in motion. Offline or `queued-offline` from the tender → CHECKOUT101 toast; from the boundary → no completion, debug log, the order stays `pos-partial`.
- **Void.** Offline → every live row is a refused `VoidPaymentsFailure` with the offline message (PAYMENT221); nothing voided locally. Online, `voidPayments` stops offering rows the server never voids (today it sends every live row, `void-payments.ts:55`): a captured row named in any `_wcpos_completions[].payment_ids`, and a captured non-manual row (D5's adopted `source: woocommerce` tender among them). Those leave the balance only through a refund (server SPEC §4.5-§4.6).
- **Terminal.** `patchAndEnqueue` throws `offline_unavailable` (unreachable while device tiles are disabled offline).

**PR B — the outbox is the sync engine's own queue** (shape (a)).
- **Model.** `MutationOperation` gains `'command'`; `RecordMutation` gains `command?: { kind: 'record' | 'capture' | 'void' | 'close'; target: string | null; commandId: string | null; body: Record<string, unknown> }` and drops `expectedEpoch`. Following the pre-GA rule (`storeScopeIdentity.ts:55-66`), the queue schema changes **at version 8** and `SCOPE_DATABASE_GENERATION` moves 7 → 8; no v9 migration. `drainable-generation.ts` becomes generation 7's shipped schemas (queue v8 with `expectedEpoch`, operation enum `['create','update','delete']`, no `command`), and generation 7's rows (protocol 3, document writes only, since PR A queues no money) drain normally. Generation-6 databases are then purged (§1.5 PR A, lifetime); they hold only parked protocol-2 work. PR A's command journal lives in the store database, not the scope database, so the 7 → 8 move does not touch it: an unresolved command from generation 7 is still in the journal, with its identity, body and approval, and still gates the tender.
- **Enqueue.** Always `append`; never coalesced or a coalesce base; `explicit: true`, so the open-cart hold never holds a command and its prerequisite chain is released (`drainMutationQueue.ts:709-717`); `isOpenCartHoldCandidate` is false for `command` (`open-cart-hold.ts:51-56`), so the settled-snapshot discarder never removes a chain containing one (`order-pull-guard.ts:155-180`). Dirty-marks the resident. A never-pushed create→delete chain annihilates its commands with it.
- **Drain order.** A command is claimable only when its record has a `remoteId` **and** no `create`/`update` row for that record is pending, claimed or held, regardless of `seq`; so born-twice follow-ups, dead-letter requeues and recovered creates (`write-intents.ts:1123-1148, 1243-1304`, `write-placement.ts:38-65`) always land before the money command they precede. **A rejected prerequisite keeps blocking across drains, through requeues.** At enqueue a command row records `prerequisites`: the mutation ids of its record's `create`/`update` rows queued before it. A command's `prerequisites` are **immutable**: they hold the original ids and are never rewritten. Every document row carries an `identity` field, its own `mutationId` when first enqueued. A replacement row (dead-letter recovery, `write-intents.ts:1140-1157`; born-twice follow-up, `:1243-1304`) is written with `replaces: <predecessor's identity>`, the original id, collapsing the `requeuedFrom` chain into one field. That write happens **before** the predecessor is removed (recovery already enqueues first and retires second, `:1132-1153`). The queue's `transact` is an in-process promise chain, not a crash-atomic or cross-tab transaction (`recordMutationQueue.ts:184-214, 240-246`), and this ordering needs none. A crash or a competing tab between the two writes leaves at worst two rows naming the same original, and the drain blocks the command on **either**. A document row is a prerequisite of a command when its `identity` or `replaces` is in the command's set, so the successor's tail `seq` (`recordMutationQueue.ts:281-290`) is never what decides, however many requeues happen. The drain seeds `blockedRecords` for commands only (`drainMutationQueue.ts:518-529`) with every command that has a prerequisite in `pending`, `claimed`, held or `rejected` state, until it is acknowledged or discarded by the cashier. A rejected row outside the set (a later, unrelated edit) does not block. Document rows keep today's behaviour.
- **Revision without a naked stamp.** A command's `revision` is read at claim from `sync.revision` when it is a stamp. Otherwise the drain fetches one **ephemerally**: the same read `refreshRevision` makes (`write-drain-lane.ts:568-601`), passed to this push only, never written to the resident. The manual rebase (`conflict-resolution.ts:364-385`) of a parked command row re-anchors the row's own revision and leaves the resident's `sync.revision` alone. The only revision writes a command causes are the ones that come with an adopted document.
- **Router.** `'command'` → `postMoneyCommand` (new, `sync-core`): 2xx → `acknowledged` with `currentRevision: null` and no document; 409 stale → `conflict` (`currentRevision`, `current`), so the order carve-out re-sends once (`write-drain-lane.ts:554-567`) and a second conflict parks (SYNC221); 409 `wcpos_order_already_paid`, `wcpos_amount_exceeds_balance`, `wcpos_balance_outstanding` and other 422 → `permanent` dead letter with the verdict (PAYMENT511/SYNC201) plus a `money-command-refused` event core turns into the tender's attention entry; 5xx/network → backoff; 401 → session wall. A requeue copies `command` verbatim.
- **Command acknowledgement.** Its own bookkeeping, not `facet.reconcile`'s: remove the mutation id from `pendingMutationIds`/`dirty` and write **no** revision (`collection-descriptors.ts:393-400` would otherwise stamp a document it never saw). Then **adopt a document**: `facet.fetchServerDocument` + the pull boundary. When successors are still queued the adoption is protected; the last successor's ack adopts the document and graft carries server-owned meta meanwhile (`:364, 669-680`); when none remain, the fetched document and its stamp land together.
- **Offline cash.** Enqueue the `record` command first, then patch the resident local-only (`_wcpos_payments` + `derive()` status); a failed patch logs PAYMENT111, the acknowledgement's adoption heals it.
- **Offline device authorization.** The **initial** authorization enqueues one `record` (`status: 'authorized'`, `recorded_offline: true`, the offline intent's `provider_refs`), body frozen. Later settlement references (`service.ts:199-205`) never re-enqueue `record` (a second body for the same id is 422). They are made durable at once as a **queued `capture` command** for that row (body `{ context: { provider_refs } }`, frozen, its own `command_id`), seq-ordered behind the `record`; the queue row, not the local ledger, is their durable copy, so the `record` acknowledgement adopting the server ledger (`collection-descriptors.ts:650-680`) cannot erase them, and a restart rebuilds nothing (`use-terminal-payments-service.ts:214-232` no longer needs the resident's refs for a queued capture). The service's in-memory capture path (`service.ts:186-230`) is used only for an online authorization; for an offline one it defers to the queued capture (`hasQueuedMoneyCommand`).
- **Till finish for an offline authorization.** D6 keeps the server order `pos-open` until capture. The till uses `tillBalance = balance − Σ offline-authorized rows (isSettledPaymentRow)`: the tender offers nothing more once it is 0, `isSaleComplete` for the `terminal` source compares `tillBalance` (`sale-completion.ts:272-273`), and `settlesSale` (`use-terminal-payments-service.ts:52-58`) accepts an open status when `tillBalance` is 0 through an offline authorization. The receipt shows the authorization; the order stays in open orders, paid in full pending capture.
- **Close and void.** Zero balance offline → queued `close`. Void offline goes through `withdrawMoneyCommand`, which follows the order-pull guard's bookkeeping-before-removal order (`order-pull-guard.ts:129-132, 166-180`):
  1. a local-only write stamps the ledger row `withdrawing: <mutationId>` and removes that id from `pendingMutationIds`/`dirty`;
  2. `removeNeverAttempted(mutationId)` (new; reuses `removeIfUnchanged`, `recordMutationQueue.ts:405-453`) removes the queue row only when it is pending, unclaimed and `attempts === 0`, under the stored revision;
  3. on success a local-only write sets the row `voided` and drops `withdrawing`; on refusal (claimed by another tab, or attempted with a lost answer) it restores the pending id, drops `withdrawing`, and queues a `void` command behind the `record`.
  An interrupted withdrawal leaves `withdrawing` on the row; the next engine start finishes it from the queue's truth (row gone → step 3 success; row present → step 3 refusal), so counted money always has either its command or a recoverable withdrawal. Card legs stay refused.

**Why (a), not a separate outbox (b).** The requirement is ordering behind the order's own document writes, and only this queue knows them; it already has durable rows, leases, a leader-serialised multi-tab drain, re-stamping, the 409 carve-out, backoff, the 401 wall, dead letters with verdicts, and the previous-generation drain. Cost: one operation, one router branch, command-specific acknowledgement, one generation bump (shared with §1.6's field removal).

Deleting it would bring back the re-settle loop ADR 0032 deleted: a diverged order would be re-derived and re-pushed on every write. So `serverOwnsMoney(meta)` keeps exactly one rule, "the durable hint says server", with no contract argument, and the hint writer always writes.

### 1.7 Refunds (PR C)

**Ground truth (Pro `next`).** `POST wcpos/v2/orders/{id}/refunds` is Pro's `Order_Refunds_Controller` (`includes/API.php:92, 110`; `API/V1/Order_Refunds_Controller.php:124-156`). Allocations over captured rows, newest first (`Payments/Refund_Processor.php:280-333`), each through free `Ledger::refund()`. WooCommerce's `api_refund` is the plan's, false for ledger plans (`:462`, `RefundPlan.php:115-117`); the client's is read only without `refund_destination` (`:231-241`). Answers carry `refund_result.allocations[{ payment_id, method_id, amount, status, provider_ref }]`. A leg that fails before any leg succeeded throws inside WooCommerce's refund creation, which deletes the refund, and the till gets the ledger's error (`Refund_Processor.php:375-380, 486-507`). A leg that fails **after** one succeeded stops the loop: the refund stays (HTTP 201), the order gets a note, and the answer lists that leg with `status: 'failed'` and `error` (`:381-395`). That `failed` is a **response** outcome only: the ledger stores no failed allocation on the refund path, because a definite provider refusal withdraws the reservation (server SPEC §6.1). The server agent's "failed comes only from a later settle" is about stored allocations; both statements hold. A leg's stored allocation is `succeeded` or `pending` (`:396-401`). Two answers are new under ADR 0040: 409 `woo_rxdb_sync_record_locked` (the first leg's reservation could not be verified; nothing reached the provider; WooCommerce deleted the refund; Pro **cached** the error under the key, `:129-140, 507`), and a 2xx after which the order summary reads `refund_pending > 0` (sent and unconfirmed). Idempotency: the key is checked for conflict, then a cached result is replayed, then reserved (`:106-121`); a held reservation answers 409 **`wcpos_idempotency_in_progress`** and a different body under the key 409 `wcpos_idempotency_conflict`, neither cached (`Payments/Idempotency_Repository.php:127-140`); plan and execution outcomes, including errors, are cached 24 h (`Refund_Processor.php:129-145`).

**Change.**
- **`api_refund` leaves the payload** (`buildRefundPayload`, `use-refund-mutation.ts:50-55`); `refund_destination` carries the choice. Pro reads `api_refund` only when `refund_destination` is absent (`Refund_Processor.php:231-241`), which the till never sends; dropping it means no path can hand `true` to a server without that override.
- **The key.** Minted per form submission and held with its frozen body until the outcome is definitive:
  - **kept** (retry re-sends the same key and body): no answer, timeout, `wcpos_idempotency_in_progress`, and a non-JSON body of any status (a proxy error proves nothing was cached);
  - **spent** (a retry is a new submission, same body, new key): a 2xx, or any WordPress error body (`{ code, data.status }`, 4xx or 5xx) other than the two idempotency codes, because Pro cached it (`:129-140`). That includes 409 `woo_rxdb_sync_record_locked`: the refund was deleted and nothing was sent, so the till retries **the same request body under a new key** (the same key would replay the cached 409 for 24 h);
  - `wcpos_idempotency_conflict` is a client bug: logged PAYMENT999, key kept, no automatic retry.
- **Outcomes.** After a 2xx the mutation refreshes the order (as today, `:123-143`) and returns `refund_result.allocations` with the refreshed summary's `refund_pending`. `refund-failure.ts` reports a `pending` allocation, or `refund_pending > 0`, as REFUND_OUTCOME_UNKNOWN (PAYMENT311, "sent to {method}, not confirmed"), and the form offers no retry for it (the provider may have refunded). A `failed` leg after a succeeded one is a partial refund naming the leg, never success. `woo_rxdb_sync_record_locked` reads "the store was busy; nothing was refunded; try again".

**Pins** (`orders/refund/use-refund-mutation.test.ts`): `the refund payload carries refund_destination and no api_refund`; `a retry after no answer re-sends the same key and body`; `wcpos_idempotency_in_progress keeps the key and the later retry replays the stored result`; `a non-JSON 502 keeps the key`; `woo_rxdb_sync_record_locked retries the same body under a new key`. Control (today every call mints a key): `a cached wcpos_refund_not_allocatable spends the key`. `refund-failure.test.ts`: `a 2xx whose summary reads refund_pending > 0 is reported as unconfirmed with no retry`; `a failed leg after a succeeded one is a partial refund`.

### 1.8 Receipts name the completion (PR C)

**Ground truth.** The receipt's fiscal block reads the write-once till tuple (`_wcpos_sale_time`, `_wcpos_sale_tz`, `_wcpos_sale_counter`, `_wcpos_register`) (`receipt/utils/build-receipt-data.ts:981-993`), which describes completion 1 only. The server appends `_wcpos_completions[n] = { id, n, at_gmt, sale_time, sale_tz, register, session, counter, total, payment_ids, reopened_at_gmt }` per completion (server SPEC §4.4).

**Change.** A receipt names a completion only from an **authoritative standing entry**: the latest `_wcpos_completions` entry has `reopened_at_gmt: null`, and the resident holds a document adopted through a **post-answer read barrier**. Only one adoption qualifies: the forced refresh that `settleMoneyCommand` issued **after** the completing command's answer. When that refresh adopts, it records `{ adoptedAfterAnswer: true, adoptedRevision }` on the journal chain. The receipt requires that flag **and** `sync.revision === adoptedRevision`, so a pre-answer read adopted later (whose adoption is newer but whose content is older) replaces the document and withdraws the authority. A local adoption time alone never qualifies. Then `buildReceiptData` takes `sale_time`, `sale_tz`, `sale_counter` and the register id from that entry and adds `fiscal.completion = n`; with `n > 1`, `fiscal.corrects` names entry `n − 1`'s id. If the latest entry is marked reopened, or the barrier does not hold (the post-answer refresh has not landed, or a later adoption replaced its document), the receipt prints **no completion number and no counter**: it never relabels the current sale with a historical entry, and `settleMoneyCommand` is retried before printing when online. With no history at all (a sale completed before ADR 0040 shipped) the till tuple stays the source, as today.

**Pins** (`receipt/utils/build-receipt-data.test.ts`): `a re-completed sale prints the latest completion's register, time and counter, with completion 2 and corrects naming entry 1`; `completion 2 succeeds but the refresh fails: the receipt prints no completion number and is never labelled completion 1`; `a latest entry marked reopened is never printed as the standing completion`; `a pre-reopen completion-1 snapshot adopted after completion 2 answers cannot label the receipt completion 1`. Control: `a sale without a completion history prints the till tuple`.

## 4. Decisions this spec makes that Paul should see

1. **A command answer's revision is never written to `sync.revision`.** It is kept in the journal's chain and sent by the next command unless the resident adopted a newer server revision since (`sync.adopted`, bound to the exact revision adopted); the mirror always upserts the answered row and writes status only under the stamp the command was sent with, and the document and its stamp arrive together by a forced refresh after the mirror (one GET per command). Alternatives: the revision alone (the next pull skips the server's payment fields) or the server returning `current` on 2xx (saves the GET; a server change).
2. **Status is an intent, never an echo**, across every producer: coalesce, full push, dead-letter and born-twice recovery, both forms. Under ADR 0040 a stale `pending`/`pos-open` is a reopen. Cost: a status change must be named.
3. **`intent`, `submit` and `close` re-check the cashier's approval (total and currency)**, frozen at the press before any provenance push, against the server document for the revision being sent and again after a stale answer; a protected adoption never authorizes a re-send, and a changed but covered total is not closed without renewed approval. `record`, `capture`, `void`, `cancel` re-send once on stale because the server re-checks the money.
4. **Every money command is journaled in the store database until a definitive outcome, and a retry is always a re-send of the frozen body.** There is no resolution by reading and no marker on the order. A command refused locally before `sentAt` is terminal and re-approved. The store database is per store, not per scope generation, so no order write, pull, reset or generation bump touches the journal. Chosen over the orders collection's local documents (which a generation bump would have to carry) and over pulling PR B's queue row into PR A (a queue schema change, and the queue cannot hold interactive card legs).
5. **Queue rows written by a protocol-2 client are parked, never sent or reconciled** (Paul's ruling, 2026-10-20, D1's reasoning: no shipped client has the payments ledger; a pre-upgrade queue holding offline ledger rows or a copied status is a dev-till artefact). Mechanism: PR A moves the scope generation 6 → 7 and the previous-generation drain refuses a generation below 7 — no push, no carry-over — reporting it as PAYMENT201 in Store health. Nothing in the new database is frozen (every order re-ingests from the server); the cost is one re-sync per till and a dev till's unsent open carts staying in the parked database.
6. **The offline outbox is the sync engine's queue** (`operation: 'command'`, explicit, drained after its record's document rows and blocked by a rejected earlier one, its own acknowledgement, no naked revisions), not a second outbox. PR B changes the queue at version 8 and moves the generation 7 → 8, per the pre-GA rule, instead of a v9 migration.
7. **PR A refuses offline tenders, the offline zero-balance close and offline voids** with visible reasons; offline cash returns in PR B.
8. **Provenance rides completion-capable commands**; a counter is allocated only for a re-completion (a refused one leaves a gap, as today: `zero-balance-completion.ts:42-44`).
9. **Server PR 5 is already merged, so PR A lands protocol 3 and the 1.3 envelope-key deletion in one PR, the deletion committed first**; never the bump alone (a protocol-3 till with the gate 400s every order update).
10. **Refunds drop `api_refund`** (Pro decides it from `refund_destination`); the key survives every unresolved outcome and is spent on a 2xx or any cached server answer, including `woo_rxdb_sync_record_locked`, which retries the same body under a new key.
11. **An offline card authorization finishes the sale at the till (`tillBalance` 0) while the server order stays `pos-open` until capture** (D6); it stays visible in open orders, paid in full pending capture.
12. **The money-owner hint stays; the `_wcpos_money_owner` stamp and the epoch keys go.** The server agent asked to delete all of it. The hint answers ADR 0032's question (who owns a diverged order's line-money aggregate), not ADR 0040's (what is paid); it is client-written and round-trips as plain meta; deleting it brings back the re-settle loop ADR 0032 removed. `serverOwnsMoney` keeps one rule with no contract argument (§1.6).
