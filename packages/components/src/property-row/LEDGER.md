# Behaviour ledger: `property-row`

Created 2026-10-25 for the property-rows grammar Paul chose after five boards (`~/Projects/wcpos-handoffs/2026-10-25-property-rows-system.html`, `2026-10-25-property-rows-every-form.html`). Numbers are assigned once and never reused; every line keeps its evidence.

**Job:** Show a record or a settings page as a list of facts, one row per fact (key · value · verb), with a record's absent facts offered as add buttons at the bottom.

**Not its job:** deciding which facts are asked for or present (`useFieldPresence` in core and the record's own field list), saving (the form's autosave). `SettingsRow` and `LockedRow` were deleted into this row on 2026-10-28 (card 5, second half); settings LEDGER lines 2 and 4 moved here as lines 9 and 12.

**Base:** React Native `View`, `Text` / `TextClassContext`, `Button`, `DocsLink`, `Switch`, and from `form/`: `FormItem`, `useSavedName`, `SavedMark`.

## Lines

1. Rows have no dividers; they separate by rhythm alone, as settings rows do (settings LEDGER line 1) — evidence: the system board, "no divider between rows"; test "renders the key, the value and the trailing slot, with no divider".
2. The key is `w-32` (128) off a phone in muted `text-sm`; the value is `text-base` foreground, set through `TextClassContext` — evidence: the system board's "one new ladder role" table; same test.
3. Off a phone (`useIsPhone`, line 18) key, value and trailing share one 44 line (`min-h-ctl`); on a phone the key stacks above the value and the trailing slot stays on the key's line, out of flow (the SettingsRow rule, settings LEDGER line 4) — evidence: the system board's implementing rules, "Phone: the key stacks above the value under md".
4. An open compound's parts are rows with `indent`: the key moves in one gutter (`pl-4`) — evidence: the board's "Compound, open: its parts are rows, indented one gutter"; test "pads the key of a part…".
5. Add buttons are `Button variant="outline" size="sm" leftIcon="plus"` (36), wrapping with `gap-2`, never Chips: a Chip is a selectable state and these are actions (CODING_STANDARDS § Chips, badges and switches) — evidence: the system board, "Add row"; test "an add is a 36-tall outline Button…".
6. Verbs are `Button variant="link" size="sm"` (primary, 13 medium), never a chevron — evidence: the board's verb vocabulary; test "a verb is a small link Button in primary ink".
7. An empty asked-for value reads as a placeholder in muted ink (`PROPERTY_PLACEHOLDER_CLASS`), shared with `EditableField`'s placeholder so the two never disagree — evidence: the board's "Asked but empty: a placeholder verb, no box".
8. ~~The row reads the form's Saved name: `name` (the field or fields it holds, `id` by default) decides whether the mark shows, and the mark takes the verb's place, never beside it; a trailing `control` (a Switch) comes after it, so a mark arriving never moves the control. Nine wrappers (PrinterRow, OrderRow, CartLineRow, CouponRow, CatalogueRow, the customer and address rows, tax IDs, custom fields) each re-derived this; a list (tax IDs, custom fields) names its field on its first row only — evidence: card 5 of the 2026-10-28 component-library review; test "the row owns the trailing slot".~~ (struck 2026-11-09, superseded by line 21: since #3333 the mark sits with the key and the verb keeps its place)
9. The row is the form item: the list's `prefix` (or the row's own) and `id` give the testID `<prefix>-row-<id>` and the item id `<prefix>-<id>` (minted without them), the key is `<item>-form-item`, a label-less control in the row adopts it, and pressing the key presses that control (focus, toggle). It needs no react-hook-form provider, so the customer-display page's rows render as the others (moved from settings LEDGER line 2) — evidence: tests "the row is the form item…", "pressing the key acts on the control it names".
10. Set elsewhere is locked (rule 6): the value, then where it is set and _Open ↗_ (`DocsLink`) when there is a link; a boolean value is a disabled switch, an empty one a dash. Used today by the order's payment, the customer's username and role, and a product's variations; and the settings pages' locked rows (replacing `LockedRow` and their "Set in WooCommerce, mirrored here" note line) — the orchestrator's pick, Paul to confirm; dropping Open is the one `DocsLink` line in the row — evidence: the property-rows system board, "Locked: value plus where it is set · Set in WooCommerce · Open ↗"; test "locked (rule 6)…".
11. A derived value (rule 5) reads in muted ink; its verb breaks the link — evidence: the board's "Derived: value in muted"; test "a derived value reads in muted ink".
12. The key column is the list's, off a phone: 128 (`w-32`) in a dialog, `PropertyList wide` (every `SettingsSection`) 256 / 288 (`w-64 lg:w-72`) with the value in one 320 column (`max-w-80`); on a settings page's one line a switch row with no value puts its `control` in that value column, at its start (`items-start`), not in the trailing slot, so a switch sits where the other rows' values sit and never where a locked row's "Set in WooCommerce · Open" sits (Paul, 2026-11-08: "not positioned correctly"); on a phone or stacked the control keeps the key's line (line 3), and in a dialog the row stays bare (line 19) (moved from settings LEDGER line 4, where they were `SettingsRow`'s) — evidence: the board's "the key column is w-32 in a dialog and md:w-64 lg:w-72 on a settings page"; tests "the key column in …", "on a settings page a switch row's control sits in the value column, not the trailing slot", "on a phone a switch row keeps its control on the key line".
13. `stacked` puts the key above the value at every width with the trailing slot on the key's line: a value too big for the line keeps its Saved mark in the row instead of an absolutely placed one (the theme tiles, the icon sets, the scan sounds and the scan volume). Only the one-line layout takes `align`'s cross-axis `items-center` / `items-start`; a stacked column keeps the default stretch, so its key and value sit at the left edge, never centred (fixed 2026-10-28 on #3023) — evidence: card 5 ("the saved mark is hand-placed at 5 offsets"); test "the key column in stacked".
14. `help` is one line under the key in the help rank — evidence: CODING_STANDARDS § Design 11 ("the help line says what happens at the till"); test "the key column in …".
15. A `compound` row (two or more controls in the value: a custom field's key and value) resets the item context for its value, so each control keeps its own name and message id; the row stays the item for its key — evidence: Codex P2 on #3011; test "a compound row keeps each control its own name and message".
16. A setting is this row (2026-10-28, card 5 second half): every settings page's rows are `PropertyRow`s in `SettingsSection`'s wide list, so a setting takes the record row's rhythm (44 tall, `py-1`) and its value column starts after the key; a switch is the row's `control`; nested settings are `indent`ed rows (rule 8), not a padded group — evidence: the property-rows board, "Settings › General — SettingsRow is this row"; tests `general.test.tsx`, `tax.test.tsx`, `theme.test.tsx`.
17. A trailing slot that carries words wraps on a phone: a locked row's provenance ("Set in WooCommerce · Open ↗") and a text verb ("Use a different address") sit in flow under the value, so they never lie over a long key on a phone; only a Saved mark and a control (a Switch), which are narrow, keep the key's line out of flow — evidence: Codex P2 on #3016 and the orchestrator's extension to verbs; test "on a phone, words wrap in flow under the value…".
18. The row stacks at the app's one layout boundary, `useIsPhone()` (768 × 480, `lib/device`), read as a hook into its classes, never at a width-only `md:`: a phone on its side (844 × 390) reads `md` and laid its rows out as a tablet's, and a gallery cell's `DeviceScope phone` could not reach a media query. There is no `phone:` class variant because Uniwind's native media queries read only min/max width and orientation (no height, no "or": `uniwind/src/bundler/css-processor/mq.ts`), so the 480 rule cannot be a media query. `lg:w-72` (line 12) is the one width step left, inside the off-phone layout, and is the uniwind ratchet's only `breakpoint-layout` entry — evidence: card 12 of the 2026-10-28 component-library review; test "%s: the hook and the row agree".
19. A row with no value (a switch with a help line: Tax exempt) lets its key and help run to the trailing slot in a dialog list; on a settings page (`wide`) the value column stays and holds the switch (line 12) — evidence: Paul 2026-11-04, "The tax exempt description text is all cramped up, it should be full length (up to the switch at least)"; test "a row with no value lets its key run to the trailing slot in %s".
20. A row with no `label` has no key column: a custom field's key is its first input, so the inputs take the width instead of a "Custom field" key repeated down the list, under one "Custom fields" `SectionHeading` (Paul 2026-11-04, second screenshot: "add a header for the manually added custom fields"); `indent` moves onto the value, and the trailing slot stays in flow at every width (no key line for a mark to sit on; Codex P2 on #3229) — evidence: Paul 2026-11-04, "The Custom Fields have a label that is repeated down the page, it seems like an unnecessary waste of value space"; test "a row with no label has no key column and indents its value".
21. The row reads the form's Saved name: `name` (the field or fields it holds, `id` by default) decides whether the mark shows. The Saved (or Not saved) mark sits with the key, never in the trailing slot (a row with no key, line 20, has nowhere else: there it leads the trailing slot, after the value), and the verb and a trailing `control` (a Switch) keep their place, so a mark arriving moves nothing. A list (tax IDs, custom fields) names its field on its first row only. `testing.tsx`, the row's test adapter, follows the same rule — evidence: `2bbc68040` (#3333, Paul 2026-11-06, after the judged real-app render); tests "one of the row's fields saved: the mark follows the key; the verb stays" and `testing.test.tsx` "marks a saved field beside the key and keeps the verb".
22. A keyed one-line row whose trailing slot carries words (a verb, locked's provenance) never squeezes its value below 160: the value column (`min-w-40 flex-1`) and the trailing slot share one wrapping line (`flex-row flex-wrap gap-x-3`), so when both do not fit the words wrap under the value, at its left edge, not under the key; where they fit the geometry is as before (the key's `gap-3`, the 12 gap, the verb at the right). Phone, stacked, a switch-only slot, a bare row, a settings page's switch-as-value and a row with no key keep their columns, with no wrapper. The tax ID input keeps the same 160 floor and wraps to its own line — evidence: a user's nl customer dialog, 2026-11 (the shipping address one character wide beside "Bewerken", the tax ID clipped to "DE12"); tests "the value and the verb share one wrapping line: %s", "a switch row with a value and no verb keeps its columns as before, with no wrapper", `tax-ids-form.test.tsx` "the tax ID input keeps 160 and wraps instead of shrinking".
