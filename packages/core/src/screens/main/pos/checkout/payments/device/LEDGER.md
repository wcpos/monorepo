**Job:** Run reader collection, server verification and durable offline authorization without collecting twice.

**Composes:** none directly.

## Lines

1. Mirror intent before collecting and verify the SDK result through the server; confirmation retry reuses that result — a confirmation failure must not ask the reader to charge again — evidence: `311ec56a05 2026-09-10 feat(checkout): app-side card-reader driver harness and the device capture-mode flow`; named retry test — platform: all hosts; physical reader use on iOS/Android.
2. Preserve a known server capture despite local mirror failure — local persistence failure is not permission to recollect — evidence: `device-leg.ts:92`, “Keep the server's outcome even if RxDB cannot mirror it; never recollect money.” — platform: all.
3. Publish the final row and outcome in the same state update — applying a paid row can unmount checkout before a later outcome notification — evidence: `device-leg.ts:101–102`, “Publish finality with the mirrored row, not after returning through another await:” / “checkout can unmount when the paid row lands, before it consumes the outcome.” — platform: all.
4. Persist offline success as authorized, not captured, before announcing completion; hold failed local writes for retry without another collection — reader approval and server settlement are distinct facts — evidence: `311ec56a05 2026-09-10 feat(checkout): app-side card-reader driver harness and the device capture-mode flow`; tests “queues offline authorization before telling the till it is paid” and “a failed offline write stays held for retry without a second collect” — platform: all; offline-reader capability dependent.
5. Preserve the original approval timestamp, reader identity and provider references across offline-write retry; require wire-compatible string/null references — retry must not rewrite where or when approval happened — evidence: `device-leg.ts:60–61`, “When the reader answered. A failed local write is retried through capture(), and” / “the approval time must not drift to the time of the retry.”; `10f2b3204e 2026-09-14 fix(checkout): the split and the reader survive offline paths, retries and re-attempts` — platform: all.
6. Leave an offline payment-intent reference empty until forwarding, reject insufficient collected amounts and do not use reader-added offline tips to pay down the remaining sale — unverified provider values must not inflate local settlement — evidence: `324a5f0644 2026-09-11 fix(stripe-driver): review pass — retryable SDK initialisation and permission recheck, offline rows carry no reference until forwarded, pos_enabled gate, native filename convention, registry subscription, friendly disconnect reasons, offline reconnect message, store precision threaded into collect`; test “offline reader-added tips cannot pay down the remaining sale balance” — platform: all.
7. Resume an online authorization by checking the server, never collecting again; mark a lost pending reader session failed durably before dismissal — application restart cannot recreate the SDK session or loop back into it — evidence: `device-leg.ts:138`, “A failed local write must not let dismissal immediately resume the pending row.”; test “resumes an online authorization by checking the server, never recollecting or claiming it paid” — platform: all.
8. Reconcile a reported decline with server status and void as needed; keep a declined result failed rather than presenting it as cashier cancellation — SDK failure alone is not authoritative provider finality — evidence: `7fb3da4789 2026-09-11 fix(checkout): device flow follow-ups from the live run — receipt stage after capture, decline lands as failed, no leg on a reader that is not connected` — platform: all.
9. Wait for in-flight intent/collection during cancellation, verify a late success and never race a void against confirmation; on-device cancellation only requests cashier action at the reader — cancellation does not prove that money was not taken — evidence: `311ec56a05 2026-09-10 feat(checkout): app-side card-reader driver harness and the device capture-mode flow`; tests “cancel waits for collection; a late successful result is still verified” and “cancel during confirmation does not race a void against the capture” — platform: all; reader interaction on iOS/Android.
10. Request cancellation at five minutes, ignore results after stop and resolve possibly-created intent before starting a fresh attempt — abandoned controllers and ambiguous requests must not create a second live payment — evidence: `311ec56a05 2026-09-10 feat(checkout): app-side card-reader driver harness and the device capture-mode flow`; tests “deadline requests cancellation at 300 seconds, and waits for the reader” and “stop ignores a late collect result” — platform: all.
