# Actions ledger

Decisions this directory lives under, one line each, appended never rewritten. Ruling:
wcpos/roadmap#421 (2026-10-09); spec `docs/specs/2026-10-09-action-event-contract-spec.md`.

1. A disabled guard stays in the chain and refuses (`actions.hook_disabled`); a disabled extension leaves it. The brief that built this said "disabled hooks are excluded", which would have let the stock guard fail open after three strikes — corrected on review, 2026-10-09.
2. Duplicate ids warn and replace outside production, throw in production, for the reason the slot registry gives (Fast Refresh and tests re-evaluate registering modules).
3. `e` is a JSON clone, deep-frozen; the caller's objects are never frozen (an RxDB payload must not be).
4. ~~After-work is not bounded by the budget.~~ Superseded by line 9: after-work has a budget of its own, so a hung after-hook cannot hold the order's queue.
5. A hook that outlives the budget gets a no-op `catch` on its promise so its later rejection is never an unhandled rejection.
6. The primitive landed alone (slice 1a) with no consumer: the stock-guard move (1b) is the next PR, because together they passed the 400-line ceiling.
7. Independent review of #2454 (first head) found three defects, all fixed with tests: an outer guard was struck for passing on an inner guard's refusal (now: the same refusal value passes through unstruck); a disabled extension could refuse a dispatch already in flight (now skipped; only a disabled guard refuses); a hook that returned without awaiting `next` let the dispatch settle before the writer (now the dispatch waits for the inner chain and a writer error propagates).
8. Second review of #2454 (head 7f3db4e5): a hook's own timer now stops when it calls `next` (an awaiting guard was being struck for a slow inner hook's time); and the chain order is reversed to **extensions first, guards last**, because with guards outermost an extension could rewrite a quantity after the stock guard had passed it. R3's "guards outermost" is amended on #421 as an overnight call; the fail-closed property it protected is kept (a guard still refuses before the writer), and what it loses is that a refusal no longer saves the extensions' work — and, found by the third review, that extensions now run before guards on the clock and before them in the return path, which lines 10 and 11 answer.
9. Bots on the third head (#2454): a hook that calls `next` synchronously got a timer anyway (now none when `nextCalled` is already true); after-work that never returned left the dispatch pending forever (now a fresh budget of the same length starts when the inner chain settles; on timeout the hook is struck and the inner answer stands); a rewrite that could not be cloned was recorded as `next` called (now the clone happens first, so the throw is an ordinary hook failure).
10. Budgets are per tier, not per dispatch (third review of #2454): extensions run first and shared one deadline with the guards, so a slow extension could starve a guard into a timeout, three of which disabled it — an extension veto by the clock. Each tier's budget starts when its first hook runs.
11. Once `next` was called, the chain's answer is the dispatch's answer and the hook's own return is ignored (third review of #2454): an extension's after-work returning its own value, or nothing, could otherwise replace or lose a guard's refusal.
12. Fourth review of #2454: two regression tests could not fail (the context's default clock captured `Date.now` by reference, so fake timers never drove the budgets — now a closure; the sync-`next` test now counts timers), the latency claim is corrected (two budgets before the writer, plus one after-work budget per hook that awaited `next`), and a guard's refusal is frozen on the way out so no extension can edit it in place.
13. Slice 1b (the stock guard as the first hook): toast ownership stays with the guard (it logs the same rows with the same toast titles as the hook it replaced); consumers that cannot toast rely on the caller showing `reasonKey` + `params`. The callers map a refusal to `false`, today's return value.
14. `cart.line.update` carries `options.skipStockGuard` in its payload so the existing bypass keeps working; the guard reads it. A consumer-specific flag in a generic payload, accepted for one consumer.
15. The two stock functions register under distinct ids (`stock.guard.add`, `stock.guard.update`); `createDispatchToken` left the barrel and the order mutation queue imports it from `registry.ts`; the dispatcher's own refusals are frozen like a guard's; the three `actions.*` reason keys have English catalog entries.
16. A guard's refusal is cloned before it is frozen (Greptile on #2454's final head): freezing in place would freeze any shared object the guard put in `detail`. The README rule that `detail` holds plain data stands; the clone makes a slip harmless.
17. Independent review of #2455: the dispatcher's own refusals were swallowed into a silent `false` and only the third strike was logged. Now every strike logs a row with its reason and error, and a caller shows any refusal the hook did not mark `presented` through `presentActionRefusal(ctx, refusal)`. The stock rows keep their category `wcpos.pos.cart.stock`: `ctx.log` takes an optional `category` (the logs screen filters by prefix, so a moved category would have emptied the cart-stock view); the default is `wcpos.pos.actions`.
18. Second review of #2455 found that a timed-out guard kept running and toasted later (its `ctx.log` still worked). Each hook now gets its own view of the context whose `log` is silent once the dispatch has settled it; after-work before the hook returns still logs. Writer-level tests now cover presentation on update and the single toast on a stock refusal; writer tests reset strikes between cases.
19. `prepareSale` stays whole for the legacy webview path (`use-checkout-session.ts`); the tender flow reaches the same gates through `register.gate` and `session.gate`. When the webview path dispatches too, `prepareSale` goes.
20. The tender commit runs inside the order's mutation queue (roadmap#421 Q2): a cart edit for that order waits for the manual leg's POST or the hand-off of a terminal leg to its service. Nothing on the leg path re-enters the queue for the same order, so there is no self-wait.
21. Independent review of #2457: `requireOpenSession` writes (a pre-action snapshot reset), so the session gate now reads through `findOpenSession` and the write stays in the tender's bottom handler before the attempt record, as `prepareSale` ordered it; the tender amounts are not rewritable in v1 (the split plan, provenance and completion facts are computed from the entry before the dispatch); a money path names its `requiredGuards` and the dispatch refuses with `actions.guard_missing` if one is not registered.
22. Bots and the third review of #2457: a commit whose balance moved while it waited for the order queue is refused inside its slot (`pos_checkout.order_changed_retry`) before any gate or leg, because the keypad's facts were read at render; the manual writer takes the gate's stamped ids (`session` on its input) instead of resolving the session a second time, and the tender flow is its only production caller, so the tender test asserts the ids it passes and the toast the refusal shows.
23. `checkout.complete` has no guard: money has moved. Its first hook is the audit observer, an extension-tier after-hook that writes the `checkout.completed` row from the dispatch result, so the row carries the actor and the hook ids. `completeSale` takes the caller's queue context when the caller is already inside the order's queue (the manual tender path), and enqueues for callers that are not (terminal service, replay).
24. The handler's pre-action write must land on the session the gate approved: if `requireOpenSession` returns a different id, the commit refuses through the open-register path. Found when the fourth review of #2457 asked for distinguishable ids in the test (slice 3).
25. The dispatcher's rows carry the §5 vocabulary (`actions.hook.timeout`, `actions.hook.failed`, `actions.hook.disabled`) with registry labels; the switch-off writes its own row. The fence (§4) is a ratcheting scanner under `packages/eslint` after the Uniwind precedent, not an ESLint rule: order writes are too polymorphic (`localPatch({ document: order })`, `order.incrementalPatch`, `collections.orders.insert`) for a type-blind rule, and the ratchet gives 'shrinks, never grows' for free. The scanner is name-based (an identifier with "order" as a camel-case word, through casts and non-null assertions) plus the literal `collection: 'orders'` of the engine helpers, so a writer holding an order under another name (`document` in `temporary-order.ts` and `new-customer-link-bridge.tsx`, `latest` in `use-cart-settlement.ts`) or behind a helper (`patchTemporaryOrderPayload`; `pushDocument(order)` in `pay.tsx`, `save-order.tsx` and `edit-order-meta/form.tsx`; `engine.adoptOrderSnapshot`, which adopts the server's copy) escapes it; reads that name the collection (`observeEngineQuery`, `engine.require`) are not sites; the exempt bottom handlers are listed in the scanner, every writer it recognises ratchets down under roadmap#421. The void mirror (`use-void-payments.ts`) is allowlisted, not exempt: it runs from the cashier's void, outside the tender dispatch.
26. Line 19's condition is met: the gateway-contract checkout and the external pay page dispatch `checkout.tender.commit` through `commitGatewaySale` (mode `gateway`, the whole balance, completing), so `prepareSale` and `gateSale` are gone and the two gates are the only register and session rules. A gateway sale's dispatch covers the writes before money (session write, journal, provenance); the bootstrap and checkout POSTs and the poll stay outside the order queue as they were, since a gateway hand-off can wait on a customer. The manual writer's `session` input is required: its one caller is the tender's bottom handler. `useCartStockGuard` went with it: its `checkCartStock` was a dead copy of the stock guard's refusal; `resolveStockOwnerId` now lives beside `readStockDocument` as a plain function.
27. The cart domain (spec amendment 2026-10-12, PR A): `cart.line.remove` is dispatched by `useRemoveLineItem` for every list, and the fee and shipping edits dispatch `cart.line.update` with the payload's new `type`, so one hook sees every line change; the stock guard passes any `type` but `line_items`. Undo of a removal is its own action and re-enters through `cart.line.add` with the restored line, so a guard that would now refuse it does. These writers called `localPatch` outside the order queue; each now runs inside `enqueueOrderMutation`, serialised with the tender commit. The stale-row report (uuid gone) stays with the caller before the dispatch, so a hook never sees a `null` line on an edit; a removal of a vanished line still dispatches with `line: null`, as the payload type says. The consumer is the plugin-integration family (roadmap#163, #86, #87, #88).
28. The cart domain, PR B: `cart.coupon.apply` and `cart.coupon.remove` have one writer, `coupon-line-actions.ts`, which recalculates every coupon against the product lines and patches both lists inside the order's queue slot; `useAddCoupon` validates the catalog coupon and `useAddQuickDiscount` checks exclusivity BEFORE the dispatch (reads, not effects), then hand their line to `applyCouponLine`. The cart-changed check moves into the writer, after the recalculation, and surfaces as `CartChangedError` (the hooks keep their `pos_cart.cart_changed` answer). Nothing on either payload is rewritable in v1: the discount is computed by the writer from the line it is handed. A refusal on apply is returned as the field's error sentence (`ctx.t(reasonKey, params)`), where the cashier is looking; a refusal on remove is a toast through `presentActionRefusal`. The three hooks no longer write, so they leave the fence allowlist (13 → 10 files).
29. The cart domain, PR C: `cart.customer.set` has one writer, `useSetCartCustomer`, replacing the three that patched the same four fields (the picker through `transformCustomerJSONToOrderJSON`, the new-customer form as a guest with the saved addresses, the address edit with the customer unchanged). `billing`, `shipping` and `taxIds` are rewritable; `customerId` is not (a hook may refuse a customer, not swap one). `taxIds: null` leaves the order's snapshot alone, as the new-customer form always did; an absent address is carried as `null` and written back as absent, because the dispatcher's clone drops `undefined`. The customer-link record for a born-local customer is written by the form after the attach, as before: it is not an order write; its identity is read from the billing that was written, since a hook may have completed it. A caller that names no customer (the address edit, a picked born-local customer with no id yet) does not write `customer_id`; the event carries the id the order has as the slot starts, so a link stamp queued ahead is kept. The writer lands on `queue.order ?? order`: a first add queued ahead turns the temporary order into a saved one and leaves the saved record on the slot (the other queued cart writers from PRs A and B need the same read, their own PR). The link identity is read from the order's billing after the attach, whatever a hook did to it. The bridge's stamp of the acknowledged Woo id (`new-customer-link-bridge.tsx`) dispatches the same event with `source: 'system'` inside the slot it already holds, so a hook sees the real id arrive; a refusal leaves the order a guest and the link waits for another pass (a guard that keeps refusing a system stamp toasts on every pass; no first-party guard refuses, and a consumer that does deduplicates). The stamp's payload carries `null` addresses and its bottom writes only `customer_id`, so a rewrite on a `source: 'system'` event has no effect.
